# Сертификационный риск-менеджмент ТАКТ

Документ фиксирует отдельный трек подготовки MVP к проверке, аттестации и возможной сертификации. Он не заявляет фактическую сертификацию продукта.

## Цель

- Разделить MVP-готовность и сертификационную готовность.
- Подготовить материалы для предварительного gap-анализа с аккредитованной лабораторией.
- Снизить риск поздних архитектурных переделок.
- Зафиксировать границы продукта: ТАКТ не является СКЗИ и не выполняет активное управление оборудованием.

## Трек ФСТЭК

1. Предварительная классификация продукта и целевых сценариев применения на объектах КИИ.
2. Оценка применимости Приказа ФСТЭК №239 для внедрений на значимых объектах КИИ.
3. Подготовка пакета документации:
   - границы продукта;
   - архитектура L1-L5;
   - модель угроз и ограничений;
   - матрица 26 инвариантов;
   - протоколы true positive / false positive;
   - аудиторский след;
   - `partial_observability`;
   - доказательный пакет;
   - SBOM;
   - offline-поставка.
4. Предварительный gap-анализ с аккредитованной лабораторией.
5. План устранения замечаний и повторная проверка.

## Трек ФСБ

ТАКТ MVP не должен позиционироваться как СКЗИ. Собственная криптография в доменном ядре отсутствует. Если заказчику требуется ГОСТ/КЭП, подпись выполняется внешним сертифицированным сервисом через инфраструктурный адаптер.

Риск ФСБ-трека сохраняется до юридического и лабораторного подтверждения границ продукта. Вопрос для pre-assessment: достаточно ли вынесения ГОСТ/КЭП во внешний сервис, чтобы не заводить отдельный криптографический трек для MVP.

## Бюджетные строки

- Консультация аккредитованной лаборатории.
- Подготовка эксплуатационной документации.
- Подготовка конструкторской/проектной документации, если потребуется.
- Испытательный стенд.
- Нагрузочные и функциональные протоколы.
- Проверка offline-поставки.
- Сопровождение замечаний лаборатории.
- Юридическая проверка позиционирования: СЗИ / не СЗИ, СКЗИ / не СКЗИ.

## Риск-реестр

| Риск | Вероятность | Влияние | Митигирующее действие |
|---|---:|---:|---|
| Продукт классифицируют как средство защиты информации | Средняя | Высокое | Провести pre-assessment, отделить аналитический контур от активного управления |
| Продукт ошибочно позиционируют как СКЗИ | Низкая | Высокое | Зафиксировать отсутствие собственной криптографии, вынести ГОСТ/КЭП во внешний сервис |
| Требования ФСТЭК №239 потребуют дополнительных журналов | Средняя | Среднее | Расширить audit ledger и compliance reports |
| Недостаточно доказательств по 26 инвариантам | Средняя | Среднее | Добавить true positive / false positive протоколы |
| `partial_observability` воспринимается как скрытие риска | Средняя | Высокое | Разделить риск и уверенность, явно показывать частичную наблюдаемость |
| Service Desk контекст неполный | Средняя | Среднее | Поддержать заявку, наряд, окно работ, утверждающего и основание |
| Внешняя подпись недоступна в строгом режиме | Средняя | Высокое | Fail-closed readiness gate, smoke на signer/verifier |
| Заказчик требует конкретную ОС/СУБД | Средняя | Среднее | Зафиксировать целевой стенд Astra/PostgreSQL-compatible/SQLite для MVP |

## Вопросы к лаборатории

1. Достаточно ли текущей границы “аналитический и доказательный контур” для исключения активного управления?
2. Требуется ли сертификация продукта как СЗИ или достаточно проектных/аттестационных артефактов внедрения?
3. Какой состав документации нужен для проверки применимости Приказа ФСТЭК №239?
4. Достаточно ли внешнего сертифицированного сервиса подписи для исключения СКЗИ-трека из MVP?
5. Какие требования предъявляются к хранению доказательного пакета и аудиторского следа?
6. Нужны ли отдельные протоколы на `partial_observability` и degraded-режимы?

## Roadmap

| Этап | Срок | Результат |
|---|---:|---|
| 1. Внутренняя фиксация границ продукта | MVP | `docs/product_boundary.md`, release-gates, отсутствие активного управления |
| 2. Пакет доказательств MVP | MVP | 26 инвариантов, тесты, audit trail, доказательный пакет, SBOM |
| 3. Pre-assessment лаборатории | MVP+1 | Gap-анализ, список замечаний, оценка СЗИ/СКЗИ |
| 4. Устранение замечаний | MVP+2 | Доработки кода, документов и стенда |
| 5. Решение о сертификации или аттестационном пакете | MVP+3 | Утверждённый план ФСТЭК/лаборатории |

## Критерии готовности трека

- Назначен владелец сертификационного трека.
- Есть бюджетная строка на лабораторию и документацию.
- Есть актуальный риск-реестр.
- Есть список вопросов к лаборатории.
- `docs/product_boundary.md` синхронизирован с кодом и тестами.
- `GET /compliance/mode` показывает отсутствие СКЗИ, отсутствие активного управления и обязательность решения оператора.
