# План спринтов: адаптация TAKT под ТЗ «Техлаб 2026» (единый интерфейс аналитика SOC)

Источник требований: `1. Positive Technologies  ТЗ  Техлаб 2026.pdf` (далее — ТЗ; ссылки вида «ТЗ §5.3» — раздел 5, строка 3 таблицы).
Архитектурное обоснование: TAKT используется как backend-ядро (ingest → нормализация → корреляция → кейс → решение оператора → доказательный пакет → экспорт) и каркас АРМ; достраивается «SOC-адаптационный слой».

Промпты сформулированы так, чтобы их можно было передать инженеру или агенту-кодеру с минимальными правками. Спринты по 2 недели (Спринт 0 — 1 неделя). Общий горизонт: ~13 недель без опции, +2 недели с ИИ-ассистентом.

## Спринт 1. Слой доступа к данным: коннекторы и SOC-нормализация (P0)

**Цель.** Данные не менее чем из четырёх классов источников поступают в TAKT через единый механизм (ТЗ §7.4) и нормализуются в общее событие с сущностными полями.

**Входные допущения.** Data contract из Спринта 0. Существующий ingest: `POST /events`, `POST /events/batch`, `ingest_trust.by_source`, потоковый паттерн из backtest (без материализации набора в память).

### Промпт

> Работаешь в L4 Infrastructure и L1 Domain (только аддитивные поля), L3 — новые эндпоинты.
>
> 1. **SOC-профиль события.** Расширь `NormalizedEvent` аддитивно (без слома существующих полей и тестов): опциональный блок `entities` — `host_id`, `user_id`, `process_id`, `parent_process_id`, `src_address`, `dst_address`, и список `artifacts` (`type`: `host|file|hash|process|account|address|url|domain`, `value`). Существующие OT-поля (`asset_id`, `operation`, `iec104_*`) не трогай — промышленный источник заполняет их как раньше, `host_id` маппится из `asset_id`.
> 2. **Порт источника.** Введи в `domain/ports/` порт `EventSourceReaderPort` (итератор нормализованных событий из внешнего хранилища). В L4 реализуй по одному адаптеру на класс источника из data contract (например, `importers/edr_events.py`, `importers/siem_events.py`, `importers/ndr_events.py`, `importers/ot_events.py` — имена по фактическим классам). Каждый адаптер: маппинг полей по data contract, простановка `source`, `ingest_trust` из конфига, потоковое чтение (генератор, как в streaming-backtest).
> 3. **Загрузка датасета.** CLI `python -m takt.tools.load_dataset --source <class> --path <file>` — прогон файла датасета через адаптер в конвейер `ProcessEvent` (с сохранением кейсов). Прогресс и итоги в stdout.
> 4. **Поиск по событиям.** Событийное хранилище: новая таблица `events` (SQLite) с сущностными полями и индексами; `GET /events/search` — фильтры по `source`, времени, `host_id`, `user_id`, `process_id`, адресу, типу/значению артефакта, полнотекст по payload; пагинация и `X-Total-Count` по образцу `GET /cases`. Ring-buffer «последних 64» остаётся для контекста оценки, но поиск идёт по персистентному хранилищу.
> 5. **Каталог источников.** Обнови `GET /catalog/event-sources`: класс источника (`edr|siem|ndr|ot|...`), человекочитаемое имя, число загруженных событий.
>
> Все маппинги полей покрой таблично-управляемыми тестами (по одному fixture-файлу на источник из датасета Спринта 0).

### Чек-лист приёмки

- [ ] Датасет всех 4 классов загружается CLI-командой; число событий в `GET /catalog/event-sources` сходится с разметкой датасета
- [ ] Для каждого источника есть тест «сырая запись → NormalizedEvent» на реальном примере из data contract
- [ ] `GET /events/search?host_id=...` возвращает события этого узла из **всех** источников одним списком (ТЗ §5.8: единый механизм поиска)
- [ ] Потоковая загрузка: пиковая память при загрузке 100k+ событий не растёт линейно от размера файла (тест по образцу `tests/test_backtest_streaming_100k.py`)
- [ ] Существующие тесты OT-конвейера зелёные без правок (обратная совместимость промышленного трека)
- [ ] Ошибки парсинга записей не роняют загрузку: строка пропускается, пишется в лог с понятным статусом (ТЗ §8.6)

## Спринт 2. Обобщённая корреляция и ручная корректировка связей (P0)

**Цель.** Автоматическое связывание событий из разных источников по общим признакам (узел, пользователь, процесс, адрес, артефакт) с возможностью ручной корректировки аналитиком (ТЗ §5.3) — вместо текущего ключа `asset|operation|time_bucket`.

**Входные допущения.** Спринт 1 (сущностные поля). Существующий механизм слияния: `burst_fingerprint`, `observations`, `invariant_hit_records`, merge-семантика в `ProcessEvent`.

### Промпт

> Работаешь в L1 Domain (`engines/alert_fatigue.py` → обобщение), L2 (`process_event.py`), L3 (новые эндпоинты), конфиг.
>
> 1. **Конфигурация ключей корреляции.** Секция `correlation` в `config/risk_weights.yaml`: список правил `keys` (например `- fields: [host_id], bucket_sec: 600`, `- fields: [user_id, dst_address], bucket_sec: 300`, `- fields: [artifact:hash]`), приоритет правил, режим `legacy` для обратной совместимости OT-трека. Перечень полей — из признаков корреляции Спринта 0.
> 2. **Обобщённый fingerprint.** Функция `correlation_fingerprints(ev, rules) -> list[str]`: событие порождает несколько кандидатных ключей. Конвейер ищет открытый кейс по любому из ключей (приоритет правил решает конфликт «два ключа → два разных кейса»: событие идёт в кейс правила с высшим приоритетом, а факт пересечения фиксируется как связь между кейсами `related_cases`).
> 3. **Типизированные связи.** При присоединении события к кейсу сохраняй, по какому признаку оно связано (`correlation_evidence`: правило, поля, значения). Merge-семантика прежняя: объединение `observations`, `invariant_hit_records`, max risk score с учётом `ingest_trust`.
> 4. **Ручная корректировка (ТЗ §5.3).** Эндпоинты: `POST /cases/{id}/events/{event_id}/detach` (отвязать событие с причиной), `POST /cases/{id}/events/attach` (привязать событие по id с причиной), `POST /cases/{id}/merge` (влить другой кейс), `POST /cases/{id}/split` (выделить события в новый кейс). Каждое действие требует `reason`, пишется в audit ledger и в `correlation_evidence` с маркером `manual`.
> 5. **Качество корреляции.** Расширь `scripts/eval_detection.py` (или создай `scripts/eval_correlation.py`): корпус размеченных сценариев в `tests/fixtures/pt_techlab/correlation/` — цепочки событий из разных источников с ожидаемой группировкой; метрики: доля правильно сгруппированных пар (pairwise precision/recall). Регрессионный тест по образцу `tests/test_detection_quality.py`.
>
> Ручные операции доступны только ролям аналитика (см. RBAC), пишутся в hash-chain аудит.

### Чек-лист приёмки

- [ ] События EDR и NDR с общим `host_id` в одном временном окне попадают в один кейс с двумя `observations` и `correlation_evidence` по узлу
- [ ] События с общим хешем файла связываются в кейс независимо от узла (правило `artifact:hash`)
- [ ] Property-тест: перестановка порядка событий в окне не меняет итоговый состав кейсов и `risk_score`
- [ ] `detach` события уводит его из кейса, кейс пересчитывает `risk_score`; действие видно в `GET /cases/{id}/audit-ledger/verify` цепочке
- [ ] `merge`/`split` идемпотентны по повторному запросу с тем же `request_id`
- [ ] Pairwise precision/recall на корпусе корреляции зафиксированы в `docs/pt_techlab/correlation_quality.md` (базовая линия для критерия §12.2)
- [ ] Режим `legacy` даёт прежний результат backtest byte-to-byte (OT-трек не сломан)

## Спринт 3. Карточки сущностей, артефакты и журнал находок (P0)

**Цель.** По узлу, пользователю и процессу собирается контекст двух типов — историчность и окружение (ТЗ §4.3); любая находка фиксируется в карточке инцидента без запоминания идентификаторов (ТЗ §4.5, §5.6). Роли приведены к модели ТЗ §5.13.

**Входные допущения.** Спринты 1–2. Существующее: baseline `EXPECTED_BEHAVIOR` (типичность), `context_matcher`, сущности `actor`/`asset`, append-only паттерн (`manual_permits`, `remediation_attempts`), RBAC operator/auditor/admin.

### Промпт

> Работаешь в L1 (сущности, `context_matcher`), L2 (новые use case), L3 (эндпоинты), L4 (хранилище).
>
> 1. **Реестр сущностей.** Доменные сущности `Host`, `UserAccount`, `Process` (расширение `asset.py`/`actor.py`, процесс — новая). Сущности материализуются из потока событий (upsert при ingest): идентификатор, первое/последнее появление, источники, счётчики активности по временным бакетам.
> 2. **Историчность.** Обобщи baseline `EXPECTED_BEHAVIOR` с активов на пользователей и процессы: типичность активности сущности по истории (частота операций по часам/дням, привычные пары «пользователь-узел», «процесс-родитель»). Выход — `typicality`: `typical | rare | first_seen` с объяснением (какие исторические факты дают оценку). При недостатке истории — явный статус неопределённости, не «типично» (ТЗ §6.3: при неполных данных система формирует статус неопределённости).
> 3. **Окружение.** Для сущности за окно расследования: сопутствующие события, запущенные файлы/процессы, сетевые соединения, связанные кейсы и артефакты — через `GET /events/search` по индексам Спринта 1.
> 4. **Карточка сущности.** `GET /entities/{type}/{id}/card`: историчность + окружение + связанные кейсы. Тип: `host|user|process`.
> 5. **Артефакты и журнал находок.** Сущность `Artifact` (тип из Спринта 1, значение, узел, статус проверки) и `Finding` (текст вывода аналитика, ссылки на события/артефакты, автор, время). Эндпоинты: `POST /cases/{id}/findings`, `GET /cases/{id}/findings`, `POST /cases/{id}/artifacts` (ручное добавление), `GET /cases/{id}/artifacts` (автособранные из `correlation_evidence` + ручные). Всё append-only, в audit ledger, включается в forensic bundle (`findings.json`, `artifacts.json`) и в экспорт кейса.
> 6. **Роли (ТЗ §5.13).** Расширь RBAC до: `analyst_l1` (квалификация, находки, решения по кейсам), `analyst_l2` (+ ручная корректировка корреляции, merge/split, пакет реагирования), `manager` (read-only + отчёты и статистика), `admin` (конфигурация, ключи). Матрицу «роль → эндпоинты» зафиксируй в `docs/pt_techlab/rbac_matrix.md` и покрой тестами.

### Чек-лист приёмки

- [ ] Карточка узла на датасете показывает историчность (typicality с объяснением) и окружение (события всех источников, процессы, соединения)
- [ ] Карточка пользователя и процесса собираются аналогично; `first_seen` сущность помечается явно
- [ ] При пустой истории сущности карточка отдаёт статус неопределённости, а не «типично»
- [ ] Находка с двумя артефактами создаётся одним запросом, видна в `GET /cases/{id}`, попадает в forensic bundle и PDF-экспорт
- [ ] Артефакты кейса включают автособранные из корреляции без ручного ввода идентификаторов (ТЗ §4.5)
- [ ] `analyst_l1` не может выполнить `merge`/`split` (403), `manager` не может писать (403) — тесты на матрицу ролей
- [ ] Все новые записи участвуют в hash-chain аудита; `GET /cases/{id}/audit-ledger/verify` зелёный

## Спринт 4. Рабочий стол инцидента: единое окно, граф, таймлайн, реконструкция (P0)

**Цель.** Аналитик ведёт расследование в одном окне: события всех источников, граф связей, таймлайн, карточки сущностей, журнал находок (ТЗ §4.1, §5.1, §5.4, §9.1). Реконструкция цепочки атаки «назад во времени» (ТЗ §4.6).

**Входные допущения.** Спринты 1–3 (API готово). Существующий АРМ `frontend/takt-arm`: очередь инцидентов, карточка кейса, TopologyMap, zod-валидация, e2e Playwright. Движки `causal_mesh`, `phase_time_tagger`.

### Промпт

> Работаешь в `frontend/takt-arm` (основной объём) и L2/L3 (реконструкция цепочки). Соблюдай существующие правила АРМ: API-режим через `VITE_TAKT_API_BASE_URL`, никакого активного управления, zod-схемы на все новые ответы.
>
> 1. **Рабочий стол инцидента.** Переработай `CaseDetail` в трёхпанельный рабочий стол: слева — лента событий кейса из всех источников (иконка класса источника, сущности кликабельны), центр — граф связей / таймлайн (переключение), справа — журнал находок и артефакты. Переход между событиями без смены экрана и «языка запросов» (ТЗ §5.1).
> 2. **Граф связей.** Узлы: host/user/process/address из `correlation_evidence` кейса; рёбра — типизированные связи (по какому признаку). Не ограничивайся `topology/demo-graph` — граф строится из данных кейса. Клик по узлу открывает карточку сущности (Спринт 3).
> 3. **Таймлайн.** Хронология событий кейса с фильтрами по источнику и сущности; маркеры срабатываний правил и ручных действий аналитика.
> 4. **Реконструкция цепочки (backend + UI).** L2 use case `reconstruct_chain`: от триггерного события назад по `parent_process_id` и связям «кто породил / кто инициировал» до первого инициатора (точка входа); вперёд — перемещение по сети (пары src→dst между узлами кейса). Развивай `causal_mesh` как основу. Выход: упорядоченная цепочка `entry_point → шаги → текущее состояние` + перечень затронутых артефактов. Эндпоинт `GET /cases/{id}/attack-chain`, отображение на таймлайне и графе.
> 5. **Фиксация «в один клик».** Из любого события/сущности на рабочем столе: «добавить в находки», «добавить артефакт» — без копирования идентификаторов вручную (ТЗ §4.5).
> 6. **Единый поиск UI.** Экран поиска поверх `GET /events/search` + `GET /cases`: одна строка запроса + фильтры; результат — события и кейсы вперемешку с типовыми действиями (открыть кейс, открыть карточку сущности).
> 7. **Счётчик ручных действий.** Инструментируй клики/переходы/копирования в АРМ: каждое значимое действие уходит в audit trail (уже есть паттерн `operator-actions`). Это данные для методики Спринта 0.
>
> Playwright e2e: сквозной демо-сценарий «алерт → контекст → находки → цепочка» проходит в одном окне.

### Чек-лист приёмки

- [ ] На демо-инциденте из датасета рабочий стол показывает события ≥4 источников в одной ленте (критерий §12.1 — без переключения систем)
- [ ] Граф кейса строится из `correlation_evidence` (не из статического demo-graph); клик по узлу открывает карточку сущности
- [ ] `GET /cases/{id}/attack-chain` на размеченном сценарии находит точку входа и цепочку процессов, совпадающую с разметкой
- [ ] Артефакт добавляется в кейс из контекстного меню события за 1 действие; появляется в журнале находок без перезагрузки
- [ ] Таймлайн и граф — два представления одного кейса, переключение не теряет выделение
- [ ] Каждое действие аналитика на рабочем столе фиксируется в audit trail (проверка: счётчик действий за e2e-прогон > 0 и воспроизводим)
- [ ] e2e-сценарий Playwright зелёный; `npm run test:frontend` полный прогон без регрессий
- [ ] UI не содержит кнопок активного управления (границы продукта; ТЗ §6.3)

## Спринт 5. Обогащение, оценка распространения, пакет реагирования (P1)

**Цель.** Проверка артефактов в интерфейсе (репутация, декодирование, песочница — ТЗ §5.7), поиск присутствия атакующего на других узлах (ТЗ §4.7), структурированный пакет для реагирования EDR (ТЗ §4.8, §5.11) и отчёт по инциденту (ТЗ §5.12, §4.10).

**Входные допущения.** Спринты 1–4. Существующее: паттерн интеграций с allowlist и ретраями (`siem_webhook`), forensic bundle с манифестом и hash-chain, PDF-экспорт, XAI-объяснения.

### Промпт

> Работаешь в L4 (интеграционный слой), L2 (use case), L3 (эндпоинты), frontend (панели).
>
> 1. **Порты обогащения.** `domain/ports/`: `ReputationPort` (адрес/хеш → вердикт, источник, время), `SandboxPort` (файл → task_id → вердикт), `DecoderService` — локальный, без сети (base64, URL-encode, hex). L4-адаптеры к сервисам из ТЗ §6.2 — по образцу `siem_webhook`: allowlist URL, ретраи, таймауты.
> 2. **Контроль передачи наружу (ТЗ §6.4).** Каждый вызов внешнего сервиса: проверка allowlist, запись в audit ledger (что передано, куда, кем инициировано), конфиг-флаг `enrichment.external_enabled` (по умолчанию `false` — передача только по согласованию с заказчиком). Кэш вердиктов в SQLite (TTL конфигурируемый) — повторная проверка не ходит наружу.
> 3. **UI обогащения.** В карточке артефакта: кнопки «проверить репутацию», «декодировать», «отправить в песочницу» (с подтверждением — файл уходит наружу); вердикты и статусы (`pending/ok/error`) отображаются в артефакте и попадают в forensic bundle. Ошибки интеграций — понятный статус, не молчаливый фейл (ТЗ §7.8, §8.6).
> 4. **Оценка распространения (ТЗ §4.7).** Use case `sweep_indicators`: по артефактам кейса (адреса C2, хеши, имена инструментов) — поиск совпадений в `events` по всем узлам; выход — перечень затронутых узлов с доказательствами (какие артефакты где встретились). Эндпоинт `GET /cases/{id}/spread-assessment`, панель в UI, результат можно одним действием добавить в находки.
> 5. **Пакет реагирования (ТЗ §5.11).** Use case `build_response_package`: структурированный набор `{artifact_type, value, node, recommended_action}` по затронутым узлам (из цепочки Спринта 4 и sweep). Действия — только рекомендации для EDR (`isolate_host`, `kill_process`, `block_hash`, `block_address`); TAKT их **не выполняет** — human-in-the-loop, пакет формируется после явного подтверждения аналитиком (роль `analyst_l2`). Формат: JSON + вложение в forensic bundle (`response-package.json` с включением в манифест и hash-chain). Панель подготовки пакета в UI (ТЗ §9.1).
> 6. **Отчёт по инциденту (ТЗ §5.12).** Use case `build_incident_report`: связный текст из шаблона — хронология, цепочка атаки, находки и артефакты, решения оператора с причинами, оценка распространения, статус пакета реагирования. Генерация из существующих XAI-summary + `decision_records` + findings. Экспорт: PDF (существующий механизм с юникод-шрифтом) и JSON.

### Чек-лист приёмки

- [ ] Декодирование base64/URL работает локально без сетевых вызовов (тест: сеть замокана, decode работает)
- [ ] При `enrichment.external_enabled=false` кнопки внешних проверок отключены с объяснением; ни один внешний вызов не уходит (тест)
- [ ] Вызов репутации на URL вне allowlist отклоняется; факт попытки — в audit ledger
- [ ] Вердикт песочницы отображается в артефакте и попадает в forensic bundle с checksum
- [ ] `spread-assessment` на размеченном датасете находит все узлы с посеянными индикаторами (полнота = 1.0 на fixture), без ложных узлов
- [ ] Пакет реагирования формируется только после подтверждения `analyst_l2`; содержит тип, значение, узел, рекомендованное действие; входит в манифест bundle и проходит `POST /forensic-bundle/verify`
- [ ] В пакете и API нет операций исполнения действий — только рекомендации (границы продукта, критерий §12.7)
- [ ] Отчёт по инциденту генерируется по демо-кейсу: связный русский текст, все находки и решения включены; PDF читается, кириллица не ломается

## Спринт 7 (опция). ИИ-ассистент: NL-поиск и подсказки (P2)

**Цель.** Поиск по данным на естественном языке и контекстные подсказки следующих шагов на основе LLM (ТЗ §5.10, §9.4) — строго изолированным модулем, human-in-the-loop, без утечки секретов (ТЗ §8.7).

**Входные допущения.** Спринты 1–6. `GET /events/search` и `GET /cases` с полным набором фильтров — целевой «исполнитель» NL-запросов. Rule-based подсказки Спринта 6 — fallback.

### Промпт

> Новый изолированный модуль `src/takt/ai/` (отдельный опциональный слой; L1 Domain не зависит от него). Включается только конфигом `TAKT_AI_ENABLED=1` + согласованный endpoint LLM (`TAKT_AI_BASE_URL`, ключ в секретах). При выключенном флаге ни один компонент не импортирует модуль на горячем пути.
>
> 1. **NL-поиск.** `POST /ai/search`: запрос на естественном языке → LLM транслирует в структурированный фильтр (JSON по схеме параметров `GET /events/search` / `GET /cases`; structured output, валидация pydantic) → выполнение обычного поиска → ответ: результаты + показанная пользователю интерпретация запроса («понял как: события узла X за вчера с типом артефакта hash»). LLM не получает результаты поиска — только текст запроса и схему фильтров.
> 2. **Подсказки шагов.** `POST /cases/{id}/ai/next-steps`: контекст кейса (сработавшие правила, типы сущностей и артефактов, статусы проверок, история решений) → рекомендации с обоснованием. Перед отправкой контекст проходит редактор: маскирование учётных данных, ключей, токенов и полей из конфигурируемого deny-list (`ai.redact_fields`); полные payload событий не передаются.
> 3. **Human-in-the-loop.** Ассистент не имеет write-эндпоинтов: не создаёт находки, не меняет статусы, не запускает обогащение. Каждая рекомендация в UI помечена «предложение ИИ» и превращается в действие только кликом аналитика.
> 4. **Аудит и наблюдаемость.** Каждый вызов LLM — запись в audit ledger (кто, какой тип запроса, объём переданных данных, латентность, статус); ошибки/недоступность LLM деградируют в rule-based подсказки Спринта 6 с понятным статусом.
> 5. **Документация.** `docs/pt_techlab/ai_module.md`: задачи ассистента, ограничения, правила обработки конфиденциальных данных, принцип human-in-the-loop (ТЗ §11.3).

### Чек-лист приёмки

- [ ] При `TAKT_AI_ENABLED=0` (дефолт) модуль не активен, эндпоинты возвращают 404, остальная система не деградирует
- [ ] NL-запрос «покажи события узла N за вчера» возвращает тот же результат, что эквивалентный ручной фильтр (набор golden-тестов «NL → фильтр» с замоканным LLM)
- [ ] Тест на редактирование: секрет/токен, посеянный в payload кейса, не попадает в тело запроса к LLM (перехват исходящего запроса)
- [ ] Некорректный/враждебный NL-запрос («удали кейс», prompt injection в payload) не приводит ни к какому действию — только к поисковой интерпретации или отказу
- [ ] Вызовы LLM видны в audit ledger; при недоступности LLM подсказки падают на rule-based без ошибки для пользователя
- [ ] `ai_module.md` существует и соответствует фактическому поведению

## Зависимости и параллелизация

```
S0 ──► S1 ──► S2 ──► S3 ──► S4 ──► S6
              │        │      ▲
              │        └──────┘ (API Спринта 3 нужно UI Спринта 4)
              └────────────► S5 ──► S6
                                    S7 (опция, параллельно S5–S6)
```

- Frontend-работу Спринта 4 можно начинать на неделю раньше (после закрытия API-контрактов Спринта 3) — контракты фиксировать в OpenAPI до реализации.
- Спринт 5 зависит от Спринта 2 (артефакты из корреляции) и Спринта 3 (сущность Artifact), но не от Спринта 4 — при двух исполнителях идёт параллельно.
- Демо-датасет и методика (Спринт 0) — критический путь: любой сдвиг сдвигает всё.

## Ограничения и принципы (сквозные для всех спринтов)

- **Human-in-the-loop:** ни один спринт не добавляет автоматических критичных действий; финальное решение — за аналитиком (ТЗ §6.3, границы продукта `docs/product_boundary.md`).
- **Обратная совместимость OT-трека:** промышленный конвейер (инварианты, IEC-104, ФСТЭК-пакет) остаётся зелёным во всех спринтах — это «профиль детектирования» и 4-й класс источников, а не отдельный продукт.
- **Секреты и конфиденциальность:** параметры интеграций в env/секретах, ничего в логах и промптах ИИ (ТЗ §8.2, §8.7); передача данных наружу — только по allowlist с аудитом (ТЗ §6.4).
- **Каждое действие — в audit ledger:** это одновременно требование ТЗ §5.14 и инструмент измерения критерия §12.4.
