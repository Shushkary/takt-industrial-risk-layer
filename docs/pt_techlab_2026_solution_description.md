# ТАКТ — единый интеллектуальный интерфейс расследования киберинцидентов

**Описание решения для конкурса Positive Technologies «Техлаб 2026»**

Задача конкурса: разработка единого интеллектуального интерфейса ИБ-продуктов для расследования киберинцидентов (по ТЗ «Техлаб 2026»).

Статус проекта: платформа **TAKT Industrial Risk Layer** одобрена экспертами Фонда «Сколково». Решение для Техлаб строится не с нуля, а на действующей платформе с production-контуром качества.

---

## 1. Резюме

Мы предлагаем построить единый интерфейс аналитика SOC на базе готовой платформы TAKT: конвейер «приём событий → нормализация → корреляция → карточка инцидента → решение аналитика → доказательный пакет → экспорт» уже реализован, протестирован и работает. Конкурсная разработка — это целевой SOC-слой поверх проверенного ядра: коннекторы к четырём классам источников единого хранилища, обобщённая корреляция по сущностям (узел, пользователь, процесс, адрес, артефакт), карточки сущностей с историчностью, граф/таймлайн и пакет реагирования.

Три свойства отличают наше решение от прототипов, собираемых с нуля:

1. **Измеримость эффекта встроена в архитектуру.** Каждое действие аналитика и системы фиксируется в неизменяемом журнале с хеш-цепочкой. Требуемое ТЗ «ускорение не менее 30%» мы доказываем не хронометражем на глаз, а воспроизводимым подсчётом действий из криптографически верифицируемого журнала — «до» и «после».
2. **Пакет реагирования — с проверяемой целостностью.** Механизм доказательного пакета (манифест, SHA-256 каждого элемента, цепочка хешей, корневой хеш, статус подписи, endpoint верификации) уже реализован. Контекст, передаваемый на реагирование, нельзя незаметно изменить — это прямой ответ на критерий «безопасность и управляемость».
3. **Human-in-the-loop — не декларация, а граница продукта.** В архитектуре TAKT зафиксирован запрет автоматических критичных действий: система не завершает процессы, не блокирует учётные записи, не закрывает инциденты без аналитика. Это совпадает с ограничениями ТЗ дословно и проверяется тестами.

Дополнительный дифференциатор: TAKT несёт компетенцию промышленной кибербезопасности (каталог из 26 инвариантов поведения АСУ ТП, нормализация IEC-104). Мы предлагаем включить промышленную телеметрию четвёртым классом источников — тогда единый интерфейс закрывает расследование и в корпоративном, и в технологическом сегменте. Для заказчика с КИИ это сценарий, который типовое SOC-решение не покрывает.

## 2. Проблема (по ТЗ)

Аналитик SOC расследует один инцидент в нескольких продуктах: EDR — данные хоста, NDR — сеть, SIEM — агрегация событий. У каждого продукта своё хранилище, свой интерфейс, свой язык запросов. Контекст расследования живёт «в голове» или в блокноте; значительная часть времени уходит на переключения и ручное сопоставление, а не на анализ. Поток однотипных ложных срабатываний при жёстких SLA создаёт риск пропустить реальную атаку.

## 3. Концепция решения

Единое рабочее место аналитика поверх объединённого хранилища заказчика. Система связывает события из разных источников по общим признакам, даёт единое представление по узлу, пользователю и процессу, позволяет фиксировать находки прямо в карточке инцидента и готовит структурированный контекст для реагирования. Финальное решение всегда за человеком.

```
┌─ Frontend: АРМ аналитика (React, готовый каркас) ────────────────┐
│  Рабочий стол инцидента · Граф связей / Таймлайн · Карточки      │
│  сущностей · Журнал находок · Единый поиск · Пакет реагирования  │
├─ Backend: ядро TAKT (FastAPI, работает) ─────────────────────────┤
│  Корреляция и группировка · Управление инцидентами · RBAC ·      │
│  Журнал действий (hash-chain) · Объяснения (XAI) · Подсказки ·   │
│  Экспорт и отчёты                                                │
├─ Слой доступа к данным (конкурсная разработка) ──────────────────┤
│  Коннекторы к единому хранилищу заказчика:                       │
│  EDR · SIEM · NDR/NTA · пром. телеметрия* → единое событие       │
├─ Интеграционный слой (паттерн готов) ────────────────────────────┤
│  Репутация адресов и хешей · Декодирование base64/URL ·          │
│  Песочница · Передача пакета в EDR — всё по allowlist, с аудитом │
└─ ИИ-модуль (опция, изолирован): NL-поиск · подсказки шагов ──────┘
```

\* Состав четырёх классов источников фиксируется с заказчиком (ТЗ §6.1). Промышленная телеметрия как четвёртый класс — наше предложение-дифференциатор; при ином решении заказчика подключается любой другой класс (IRP/SOAR, UEBA, песочница) — архитектура портов делает источник вопросом одного адаптера.

## 4. Соответствие целевым задачам ТЗ

| № | Целевая задача ТЗ | Как решается | База |
|---|---|---|---|
| 1 | Единое окно расследования | Рабочий стол инцидента: события ≥4 источников одной лентой, переходы без смены системы | АРМ готов, нужна SOC-компоновка |
| 2 | Корреляция и группировка | Автосвязывание по составным ключам (узел, пользователь, процесс, адрес, артефакт) + ручная корректировка связей аналитиком с аудитом | Движок слияния кейсов работает, обобщаем ключи |
| 3 | Контекст по сущности | Карточка узла/пользователя/процесса: историчность (типичность активности по накопленной базовой линии поведения) + окружение (сопутствующие события, процессы, соединения) | Механизм базовой линии `EXPECTED_BEHAVIOR` работает |
| 4 | Обогащение и проверка артефактов | Репутация адресов/хешей, декодирование base64/URL, вердикт песочницы — в карточке артефакта; внешние вызовы только по allowlist | Паттерн интеграций с allowlist готов |
| 5 | Привязка находок к инциденту | Журнал находок и артефактов: фиксация «в один клик» из контекста события, append-only, без ручного копирования идентификаторов | Паттерн append-only журналов работает |
| 6 | Реконструкция цепочки атаки | Анализ «назад во времени»: точка входа, цепочка процессов, карта перемещения; отображение на графе и таймлайне | Причинный граф — развитие движка causal mesh |
| 7 | Оценка распространения | Поиск индикаторов кейса (C2-адреса, хеши, инструментарий) по всем узлам; перечень затронутых узлов с доказательствами | Поиск по событийному хранилищу |
| 8 | Пакет для реагирования | Структурированный набор «тип артефакта — значение — узел — рекомендованное действие» для EDR; формируется после подтверждения аналитика; входит в доказательный пакет с хеш-цепочкой | Доказательный пакет работает |
| 9 | Снижение ручных действий | Целевой ориентир ≥30%; измерение — из журнала действий (см. раздел 7) | Журнал с hash-chain работает |
| 10 | Описание инцидента | Автосборка связного отчёта: хронология, цепочка, находки, решения с причинами; экспорт PDF/JSON | Экспорт PDF (кириллица) и XAI-объяснения работают |
| 11 | ИИ-ассистент (опция) | NL-поиск через трансляцию в структурированные фильтры, подсказки шагов; изолированный модуль, секреты маскируются, ассистент не выполняет действий | Новый опциональный модуль |

Функциональные требования ТЗ §5.13–5.14 (роли и журнал действий) закрыты сегодня: RBAC (роли расширяются до «1-я линия / 2-я линия / руководитель / администратор») и append-only журнал действий с эндпоинтами верификации целостности.

## 5. Что уже работает (задел платформы)

Мы сознательно разделяем «готово сегодня» и «конкурсная разработка» — это честная оценка, которую легко проверить по репозиторию и живому стенду.

**Готово и проверено тестами:**

- Конвейер ingest: приём событий (единичный, пакетный), нормализация, коэффициенты доверия по источникам, потоковая обработка 100k+ событий без роста памяти.
- Управление инцидентами: карточки с потоком событий, статусами, решениями аналитика (каждое — с причиной и request id), слияние связанных срабатываний в один кейс (защита от alert fatigue), поиск по ~20 фильтрам с пагинацией.
- Объяснимость: по каждому кейсу — какие правила сработали, вклад в оценку риска, объяснение и контрфактические условия («что должно было быть иначе, чтобы риска не было»).
- Доказательный пакет: ZIP с манифестом, SHA-256 каждого элемента, цепочка хешей, корневой хеш, статус подписи, верификация пакета по API.
- Безопасность: строгая аутентификация по умолчанию (fail-closed), RBAC, rate limiting c защитой от подмены IP, allowlist исходящих интеграций, security-заголовки, секреты вне кода и логов.
- Наблюдаемость: health/ready/live-пробы, метрики Prometheus, структурированные логи, статусы ошибок интеграций.
- Инженерный контур: CI (тесты на Python 3.11–3.14, контрактные тесты API, mutation-тестирование, e2e Playwright для фронтенда), SBOM бэкенда и фронтенда, воспроизводимая Docker-сборка, Dependabot, документированные runbook'и выкладки и отката.
- АРМ аналитика (React + TypeScript): очередь инцидентов, карточка кейса, библиотека правил, карта сегмента, аудит — уже работает с backend API, ответы валидируются схемами.
- Качество детектирования: воспроизводимый протокол true positive / false positive с регрессионными тестами.

**Конкурсная разработка (13 недель, план спринтов приложен):** коннекторы к 4 классам источников по структуре данных заказчика, обобщение ключей корреляции на сущности SOC, карточки пользователя/процесса, журнал находок и артефактов, граф/таймлайн из данных кейса, реконструкция цепочки, обогащение артефактов, пакет реагирования, измерение ускорения, опциональный ИИ-ассистент.

## 6. Архитектура и технологии

Чистая слоистая архитектура (в терминах ТЗ §7 — все пять компонентов):

| Компонент ТЗ | Реализация |
|---|---|
| Frontend | React 18 + TypeScript + Vite; валидация ответов API схемами; e2e-тесты Playwright; два режима (API / локальная демонстрация) с явной маркировкой |
| Backend | Python / FastAPI; доменное ядро изолировано от инфраструктуры (контролируется import-linter'ом); OpenAPI с контрактными тестами |
| Слой доступа к данным | Порты/адаптеры: единый интерфейс чтения источников, по одному адаптеру на класс; потоковое чтение; единый механизм поиска по всем источникам |
| Интеграционный слой | Коннекторы с allowlist URL, ретраями, таймаутами, кэшем вердиктов и журналированием каждой передачи наружу |
| ИИ-модуль (опция) | Изолированный слой, включается флагом конфигурации; LLM транслирует запрос в структурированный фильтр — исполняет запрос обычный поиск; маскирование конфиденциальных полей перед промптом |

Хранилище решения (инциденты, находки, артефакты, журнал действий) — SQLite/PostgreSQL-совместимый слой с миграциями; основной источник событий — единое хранилище заказчика, доступ только на чтение. Развёртывание — Docker / docker-compose, проверено в Kubernetes (пробы liveness/readiness, graceful shutdown).

## 7. Методика измерения ускорения (критерий §12.4)

Ключевое требование ТЗ — измеримое ускорение не менее 30% относительно зафиксированной базовой линии. Наш подход:

1. **Единица измерения** — ручное действие аналитика: клик, переключение системы, ручное копирование идентификатора, ввод запроса. Плюс астрономическое время этапов.
2. **Инструмент** — журнал действий с хеш-цепочкой: АРМ фиксирует каждое значимое действие; целостность журнала верифицируется по API. Подсчёт не допускает «подгонки» задним числом.
3. **Протокол** — один и тот же размеченный инцидент из датасета заказчика расследуется дважды: (а) «как сейчас» — поиск по каждому источнику отдельно с ручным сопоставлением; (б) в едином интерфейсе. Скрипт формирует таблицу «этап → действия/время до и после → дельта». Двойной прогон обязан давать одинаковые числа.
4. **Фиксация с заказчиком** — базовая линия и методика согласуются на старте (как требует ТЗ §12), а не после получения результата.

Ожидаемые источники экономии: исчезают переключения между продуктами (корреляция собирает события сама), исчезает ручное копирование идентификаторов (фиксация находок в один клик), сокращается сбор контекста (карточка сущности вместо обхода систем), реконструкция и оценка распространения выполняются запросом вместо ручного поиска.

## 8. Безопасность и нормативные требования (ТЗ §6.3–6.4, §12.7)

- Финальное решение по инциденту принимает аналитик; система не выполняет критичных действий — это архитектурная граница продукта, закреплённая документально и проверяемая тестами (в API и UI отсутствуют операции исполнения).
- При неполных или противоречивых данных система выставляет явный статус неопределённости (механизм оценки качества данных и частичной наблюдаемости уже работает) и оставляет решение за аналитиком.
- Ролевой доступ, журналирование всех действий, контроль передачи данных во внешние сервисы: allowlist, конфигурационный флаг внешних обогащений (по умолчанию выключен — передача только по согласованию с заказчиком), запись каждой передачи в аудит.
- Секреты — в конфигурации/хранилище секретов, не в коде, логах и промптах ИИ-модуля.
- Данные инцидентов рассматриваются как конфиденциальные; экспортируемые пакеты имеют проверяемую целостность.

## 9. План реализации

13 недель, 7 спринтов (детальный план с промптами и чек-листами приёмки — в приложении `pt_techlab_2026_sprint_plan.md`):

| Недели | Спринт | Веха |
|---|---|---|
| 1 | 0. Контракт данных | Согласованы источники, признаки корреляции, датасет, методика базовой линии |
| 2–3 | 1. Слой доступа к данным | Датасет 4 классов загружается, единый поиск по событиям |
| 4–5 | 2. Обобщённая корреляция | Автогруппировка по сущностям + ручная корректировка; метрики качества корреляции |
| 6–7 | 3. Сущности и находки | Карточки узла/пользователя/процесса, журнал находок, роли |
| 8–9 | 4. Рабочий стол инцидента | Единое окно, граф/таймлайн, реконструкция цепочки |
| 10–11 | 5. Обогащение и реагирование | Репутация/декодирование/песочница, оценка распространения, пакет реагирования, отчёт |
| 12–13 | 6. Измерение и демонстрация | Подтверждённое ускорение, воспроизводимый демо-сценарий, документация, презентация |
| параллельно 10–13 | 7. ИИ-ассистент (опция) | NL-поиск и подсказки шагов, human-in-the-loop |

Границы MVP соответствуют ТЗ §14: единое окно ≥4 источников, автокорреляция, контекст по сущностям, находки с привязкой к инциденту, пакет реагирования, измеренное сокращение ручных действий. ИИ-ассистент — вне обязательного объёма, реализуется при наличии согласованного LLM-контура.

## 10. Почему наше решение (сводка дифференциаторов)

1. **Стартуем с работающей платформы, а не с пустого репозитория.** Требования ТЗ §8 к коду и сборке (тесты, версионирование, воспроизводимая сборка, конфигурация, защита секретов) выполнены уже на старте — конкурсное время уходит на функциональность для аналитика, а не на каркас.
2. **Доказуемое, а не декларируемое ускорение.** Верифицируемый журнал действий превращает главный критерий конкурса (≥30%) из обещания в воспроизводимый факт.
3. **Пакет реагирования с целостностью доказательного уровня.** Хеш-цепочка и верификация манифеста — свойство, которого нет в типовом прототипе, и прямой аргумент по критерию «безопасность и управляемость».
4. **Human-in-the-loop как архитектурный инвариант**, совпадающий с ограничениями ТЗ дословно.
5. **Промышленный сегмент как расширение сценария.** Единственное решение, готовое показать расследование инцидента, пересекающего границу «корпоративная сеть → технологический сегмент» (синергия с PT ISIM).
6. **Внешняя валидация.** Платформа TAKT одобрена экспертами Фонда «Сколково»; проект ведётся с публичной историей изменений, аудитом и планом сертификационного трека (ФСТЭК) — зрелость процессов, а не только кода.

## 11. Ожидаемый результат

Работающий прототип единого интерфейса аналитика SOC на датасете заказчика: расследование от квалификации алерта до пакета реагирования в одном окне, с автоматической корреляцией событий четырёх классов источников, сохранённым контекстом расследования и измеренным сокращением ручных действий не менее чем на 30% — с воспроизводимой методикой, которую заказчик может перепроверить самостоятельно.
