# Схема источника: сетевой сенсор PT NAD

Источник: файл заказчика `2_5400112550773827821.json` — mapping индекса Elasticsearch единого хранилища. Это первая **фактическая** схема, полученная от заказчика по ТЗ §6.1; до неё контракт данных строился на предполагаемых именах полей.

## Состав схемы

| Параметр | Значение |
|---|---|
| Полей верхнего уровня | 145 |
| Полей всего (с вложенными) | 1786 |
| `dynamic` | `false` — новые поля индексом не принимаются |
| Типы | keyword 1082 · long 430 · date 126 · ip 49 · boolean 42 · integer 37 · double 9 · byte 7 · short 3 · join 1 |

## Идентификация класса источника

Схема соответствует **сетевому сенсору (NDR / PT NAD)**. Признаки: отпечатки TLS-клиента `ja3_md5`, `ja3_string`, `ja4`; статистика потока `bytes.sent` / `bytes.recv`, `to_client`, `to_server`, `flow_stat`, `duration`; протокольные поля `app_proto`, `app_protos`, `tunnel`, `pcaps`; поля сигнатур `s_id`, `s_msg`, `s_cls`, `s_pr`, `s_rev`, `s_refs.cve`; пассивная идентификация ОС `os_p0f`, `os_fp`.

Процессной телеметрии (идентификатор процесса, родительский процесс, командная строка) в схеме **нет** — это ожидаемо для сетевого сенсора и означает, что признак «процесс» из ТЗ §4.2 должен приходить из другого класса источников (EDR).

## Поля для корреляции (ТЗ §4.2)

Схема даёт сквозной идентификатор узла `host_id`, продублированный во всех ролевых группах — это основной ключ склейки событий по узлу.

| Признак ТЗ | Поля схемы | Замечание |
|---|---|---|
| **Узел** | `src.host_id`, `dst.host_id`, `host.host_id`, `attacker.host_id`, `victim.host_id`; имена `src.name`, `dst.name`, `host.name` | `host_id` — готовый стабильный ключ, не требует нормализации |
| **Пользователь** | `user`, `credentials.login`, `subject` | `subject` — плоское keyword-поле, не объект |
| **Процесс** | — | В схеме отсутствует; берётся из EDR |
| **Адрес** | `src.ip`, `dst.ip`, `attacker.ip`, `victim.ip` (тип `ip`); порты `src.port`, `dst.port` | Тип `ip` даёт корректную сортировку и подсети |
| **Артефакт** | `sha256`, `md5`, `fuzzy_hash`, `ja3_md5`, `ja4`, `filename`, `filepath`, `query.rrname`, `server_name`, `dst.dns` | JA3/JA4 — сильные индикаторы инструментария |
| **Техника атаки** | `att_ck` | MITRE ATT&CK; позволяет говорить на языке MaxPatrol O2 |

Дополнительно схема уже содержит **разметку ролей** — `attacker.*` и `victim.*`. Это ценно: часть работы по определению направления атаки сделана на стороне сенсора, и её не нужно выводить заново.

## Маппинг в каноническое событие TAKT

Реализация: [`src/takt/infrastructure/importers/nad_events.py`](../../src/takt/infrastructure/importers/nad_events.py). Формат чтения — NDJSON (по одному документу на строку), потоково; выгрузки `_search` с обёрткой `_source` распаковываются автоматически.

| Поле TAKT | Источник (приоритет сверху вниз) |
|---|---|
| `event_id` | `_id` → `_ndx` → `_prn.id` → `tx_id` → `file_id` → составной ключ потока `nad:<ts>|<src.ip>|<src.port>|<dst.ip>|<dst.port>` |
| `observed_at` | `ts` → `ts_start` → `_ltime` → `tx_time` |
| `source` | константа `ndr` |
| `protocol` | `app_proto` → `proto` → `protocol` |
| `operation` | `s_msg` → `alert.description` → `type` → `app_name`; приводится к верхнему регистру |
| `payload_size` | `bytes.sent + bytes.recv` → `size` → 0 |
| `entities.host_id` | `src.host_id` → `host.host_id` → `attacker.host_id` → `src.name` → `host.name` |
| `entities.user_id` | `user` → `credentials.login` → `subject` |
| `entities.src_address` | `src.ip` → `attacker.ip` |
| `entities.dst_address` | `dst.ip` → `victim.ip` |
| `artifacts` | `sha256`, `md5`, `ja3_md5`, `ja4` → HASH (нижний регистр); `filepath`/`filename` → FILE; `query.rrname`, `server_name`, `dst.dns` → DOMAIN; `dst.ip` → ADDRESS; `credentials.login` → ACCOUNT |
| `payload.mitre_technique` | `att_ck` — выносится плоским полем для корреляции и UI |
| `payload` | исходный документ целиком, **за вычетом секретов** (см. ниже) |

Дубликаты артефактов схлопываются по паре «тип + значение»: например, `server_name` и `dst.dns` с одинаковым доменом дадут один артефакт.

## Безопасность: пароли в схеме

Схема содержит поле **`credentials.password`** (`keyword`) — пароли, восстановленные из незашифрованного трафика, вместе с `credentials.valid` (проверка успешности).

Это чувствительные данные, попадающие под требование ТЗ §8.7 «секреты и конфиденциальные данные не попадают в открытые логи и подсказки ИИ-модели». В коннекторе:

- пароли и ключи из трафика заменяются на маркер `[redacted]` до записи в `payload` — в хранилище кейсов, доказательный пакет и экспорт они не попадают. Маскирование идёт по имени поля и обходит вложенность и массивы: по фактическим схемам стенда (`nad_table_schemas.json`, 38 таблиц) `credentials` объявлено как `array(row("login", "valid", "password"))`, а пароли SMB и DCERPC лежат в `rqs` (`account_password`, `case_sensitive_password`, `password`), ключи сессии и шифрования — в `rqs`/`rsp`;
- сессионные cookie маскируются наравне с паролями: `cookie` объявлен в `rqs` таблицы HTTP и отдельной колонкой в RDP, `set_cookie` — в ответе HTTP. Перехваченная из трафика сессия даёт доступ без пароля, поэтому в `payload` ей места нет;
- настройки политики паролей (`max_password_age`, `min_password_length`, `last_password_change`) не маскируются: это состояние домена, а не значения паролей;
- при ошибке разбора документа в лог пишутся только путь и номер строки, без содержимого;
- `credentials.login` сохраняется — он нужен для корреляции по учётной записи и не является секретом.

Регрессия закреплена тестом `test_nad_security_password_not_in_payload_but_login_preserved` — он проверяет отсутствие пароля во всём сериализованном payload, а не только в одном поле.

**Вопрос к заказчику:** нужно ли расширить список маскируемых полей. Уже маскируются пароли и ключи сессий; остаются кандидаты — `cookie`, `headers`, `keypressed` (перехват нажатий), `params`, `query`. Список задаётся константой `REDACTED_FIELD_NAMES` и меняется без правки логики.

## Открытые вопросы по схеме

1. **Идентификатор документа.** В mapping нет служебного `_id` (он вне `properties`). Реализован каскад `_id` → `_ndx` → `_prn.id` → `tx_id`; какое поле фактически уникально в выгрузке — требует подтверждения на реальных данных.
2. **Выбор времени.** Присутствуют `ts`, `ts_start`, `ts_end`, `_ltime`, `tx_time`. Принято `ts` как время события; `_ltime` — предположительно время загрузки в хранилище. Требует подтверждения.
3. **Формат выгрузки.** Реализован NDJSON. Если заказчик отдаёт JSON-массив или сразу ответ `_search` целиком — потребуется дополнительный режим чтения (изменение локальное, в читателе).
4. **Остальные три класса источников.** Схемы EDR, SIEM и промышленного сенсора пока не получены; их маппинги в [`data_contract.md`](data_contract.md) остаются предположительными и подлежат такой же замене.
