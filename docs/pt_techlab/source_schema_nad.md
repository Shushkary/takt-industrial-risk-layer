# Схема источника: сетевой сенсор PT NAD

Источники: файл заказчика `2_5400112550773827821.json` — mapping индекса Elasticsearch единого
хранилища, и `nad_table_schemas.json` — фактические схемы **38 таблиц** `nad_traffic_<протокол>`
витрины Trino/Kafka того же сенсора. Первый описывает документ целиком, второй — как этот
документ разложен по таблицам протоколов; маппинг построен по обоим. Это первая **фактическая** схема, полученная от заказчика по ТЗ §6.1; до неё контракт данных строился на предполагаемых именах полей.

## Состав схемы

| Параметр | Значение |
|---|---|
| Полей верхнего уровня | 145 |
| Полей всего (с вложенными) | 1786 |
| `dynamic` | `false` — новые поля индексом не принимаются |
| Типы | keyword 1082 · long 430 · date 126 · ip 49 · boolean 42 · integer 37 · double 9 · byte 7 · short 3 · join 1 |

## Идентификация класса источника

Схема соответствует **сетевому сенсору (NDR / PT NAD)**. Признаки: отпечатки TLS-клиента `ja3_md5`, `ja3_string`, `ja4`; статистика потока `bytes.sent` / `bytes.recv`, `to_client`, `to_server`, `flow_stat`, `duration`; протокольные поля `app_proto`, `app_protos`, `tunnel`, `pcaps`; поля сигнатур `s_id`, `s_msg`, `s_cls`, `s_pr`, `s_rev`, `s_refs.cve`; пассивная идентификация ОС `os_p0f`, `os_fp`.

Процессной телеметрии (идентификатор процесса, родительский процесс, командная строка) в схеме **нет** — это ожидаемо для сетевого сенсора и означает, что признак «процесс» из ТЗ §4.2 должен приходить из другого класса источников (EDR).

## Поля для корреляции (ТЗ §4.2)

Схема даёт сквозной идентификатор узла `host_id`, продублированный во всех ролевых группах — это основной ключ склейки событий по узлу.

| Признак ТЗ | Поля схемы | Замечание |
|---|---|---|
| **Узел** | `src.host_id`, `dst.host_id`, `host.host_id`, `attacker.host_id`, `victim.host_id`; имена `src.name`, `dst.name`, `host.name` | `host_id` — готовый стабильный ключ, не требует нормализации |
| **Пользователь** | `user`, `credentials.login`, `subject` | `subject` — плоское keyword-поле, не объект |
| **Процесс** | — | В схеме отсутствует; берётся из EDR |
| **Адрес** | `src.ip`, `dst.ip`, `attacker.ip`, `victim.ip` (тип `ip`); порты `src.port`, `dst.port` | Тип `ip` даёт корректную сортировку и подсети |
| **Артефакт** | `sha256`, `md5`, `fuzzy_hash`, `ja3_md5`, `ja4`, `filename`, `filepath`, `query.rrname`, `server_name`, `dst.dns` | JA3/JA4 — сильные индикаторы инструментария |
| **Техника атаки** | `att_ck` | MITRE ATT&CK; позволяет говорить на языке MaxPatrol O2 |

Дополнительно схема уже содержит **разметку ролей** — `attacker.*` и `victim.*`. Это ценно: часть работы по определению направления атаки сделана на стороне сенсора, и её не нужно выводить заново.

## Маппинг в каноническое событие TAKT

Реализация: [`src/takt/infrastructure/importers/nad_events.py`](../../src/takt/infrastructure/importers/nad_events.py). Формат чтения — NDJSON (по одному документу на строку), потоково; выгрузки `_search` с обёрткой `_source` распаковываются автоматически.

| Поле TAKT | Источник (приоритет сверху вниз) |
|---|---|
| `event_id` | `_id` → `_ndx` → `_prn.id` → `tx_id` → `file_id` → составной ключ потока `nad:<ts>|<src.ip>|<src.port>|<dst.ip>|<dst.port>` |
| `observed_at` | `ts` → `ts_start` → `_ltime` → `tx_time` |
| `source` | константа `ndr` |
| `protocol` | `app_proto` → `proto` → **имя таблицы стенда** → `protocol` → `network` (см. «Протокол из имени таблицы») |
| `operation` | `s_msg` → `alert.description` → `verdict` → команда протокола своей таблицы → `opcode` → `type` → ветка запроса (TFTP) → операция таблицы → `NETWORK_FLOW`; приводится к верхнему регистру (см. «Операция и учётная запись по таблицам») |
| `payload_size` | `bytes.sent + bytes.recv` → `size` → 0 |
| `entities.host_id` | `src.host_id` → `host.host_id` → `attacker.host_id` → `src.name` → `host.name` |
| `entities.user_id` | `user` → `credentials.login` → `rqs.user_name` → `rqs.cname.principal` → `rqs.bind.name` → `rqs.usm_sec_params.user_name` → `subject` → аргумент команды `USER`/`LOGIN` |
| `entities.src_address` | `src.ip` → `attacker.ip` |
| `entities.dst_address` | `dst.ip` → `victim.ip` |
| `artifacts` | `sha256`, `md5`, `ja3_md5`, `ja4` → HASH (нижний регистр); `filepath`/`filename`, имена файлов из запросов SMB, TFTP и NFS, путь именованного канала → FILE; `rqs.url`, `rqs.uri` → URL; `query.rrname`, `server_name`, `dst.dns`, `rqs.host`, `rqs.domain_name` → DOMAIN; `dst.ip` → ADDRESS; разобранная учётная запись и учётные записи из параметров DCERPC → ACCOUNT |
| `payload.mitre_technique` | `att_ck` — выносится плоским полем для корреляции и UI |
| `payload` | исходный документ целиком, **за вычетом секретов** (см. ниже) |

Дубликаты артефактов схлопываются по паре «тип + значение»: например, `server_name` и `dst.dns` с одинаковым доменом дадут один артефакт.

## Протокол из имени таблицы

Витрина разложена по таблицам `nad_traffic_<протокол>`, и **протокола в самом документе нет**:
колонки для него у 36 таблиц из 38 не существует. Пока протокол брался только из полей
документа, 36 таблиц давали события с протоколом `network` — по такому событию нельзя отличить
запрос DNS от подбора пароля по SMB.

Протокол берётся из имени таблицы. Перечень в
[`nad_events.py`](../../src/takt/infrastructure/importers/nad_events.py) (`TABLE_PROTOCOL`)
содержит **все 38 таблиц** и не имеет умолчания по остатку: таблица, которой в перечне нет,
означает не «протокол неизвестен», а незамеченную таблицу — её события молча стали бы сетевым
потоком. Незнакомое имя протоколом не становится.

Имя таблицы берётся из выгрузки: из поля документа (`table_name`, `_table`, `__table`), иначе
из имени файла (`nad_traffic_dns.ndjson`), иначе из явного параметра читателя. Штатный
источник — имя файла: экспорт из хранилища делается по одной таблице.

Пять таблиц протокол не называют — и это не пробел: запись потока несёт `app_proto`,
срабатывание сигнатуры (`alert`, `s_alert`), восстановленное письмо (`mail`) и извлечённый файл
(`files`, `files_old`) протоколом не являются.

Отдельно: колонка `protocol` таблицы **RDP** — это уровень защиты сеанса (`HYBRID`, то есть
CredSSP), а не протокол события. Поэтому имя таблицы в каскаде идёт **раньше** этой колонки:
иначе аналитик увидел бы несуществующий протокол «hybrid».

## Операция и учётная запись по таблицам

У каждой таблицы своя запись команды. Каскад операции разбирает поля запроса:

| Поле запроса | Таблицы |
|---|---|
| `rqs.cmd.name` | FTP, POP3, IMAP, SMTP, NFS (в NFS команды объявлены массивом) |
| `rqs.method` | HTTP, SIP |
| `rqs.command` | SMB, SOCKS5 |
| `rqs.operation.name` | DCERPC и его широковещательная таблица |
| `rqs.msg_type` | NTLM, SNMP |
| `rqs.type` | Kerberos, LDAP, ICMP |
| `rqs.options.type`, `rqs.op` | DHCP |
| `rqs.mode` | NTP |
| `opcode` | DNS |
| `type` | SSH, TLS |
| наличие ветки `rqs.read` / `rqs.write` | TFTP |
| операция таблицы (`TABLE_OPERATION`) | `CONNECT` — MySQL, PostgreSQL, Oracle TNS, TDS, RDP, RFB, QUIC, MS-NMF; `FILE_TRANSFER` — `files`, `files_old`; `PIPE_ACCESS` — `pipes`; `MESSAGE` — `mail` |

Учётная запись берётся из поля аутентификации своего протокола: `user` (MySQL, PostgreSQL,
Oracle TNS), `credentials.login` (запись потока), `rqs.user_name` (NTLM, SOCKS5),
`rqs.cname.principal` (Kerberos), `rqs.bind.name` (LDAP), `rqs.usm_sec_params.user_name`
(SNMPv3) и аргумент команд `USER`/`LOGIN` в открытом тексте (FTP, POP3, IMAP).

Аргумент команды `AUTH` учётной записью не считается: у SMTP первое слово в нём — механизм
(`PLAIN`, `LOGIN`), и логина там нет вовсе. Учётные записи из параметров вызова DCERPC — объект
операции (запись, от имени которой заводится служба), а не тот, кто действует: они становятся
артефактом и в `user_id` не идут.

### Разрешение пути через массивы

В схемах стенда `credentials` объявлено как `array(row("login", "valid", "password"))`, `query`
у DNS — как массив записей, команды NFS — тоже. Разбор только формы «объект» терял логин потока
и домен запроса **целиком**. Путь теперь проходит и через массивы: берётся первый элемент, в
котором остаток пути разрешается.

### Покрытие признаков ТЗ §4.2 по 38 таблицам

Измерено по фактическим схемам, а не по документации:

| Признак | Было | Стало | Чего нет и почему |
|---|---|---|---|
| Время | 38/38 | 38/38 | — |
| Узел | 37/38 | 37/38 | `dcerpc_br` — колонок узла в схеме нет |
| Адреса | 37/38 | 37/38 | `dcerpc_br` — колонок `src`/`dst` в схеме нет |
| Протокол | 2/38 | **33/38** | `alert`, `s_alert`, `mail`, `files`, `files_old` — протокол не называют |
| Операция | 6/38 | **36/38** | `flow` — строка и есть поток; `telnet` — в строке кусок набранного потока |
| Учётная запись | 5/38 | **13/38** | остальные таблицы учётной записи не несут |

Операция берётся тремя способами, в порядке убывания точности: поле команды протокола, ветка
запроса (`rqs.read` / `rqs.write` у TFTP — там команду называет присутствие поля, а не его
значение) и операция таблицы (`TABLE_OPERATION`) — для таблиц, где строка и есть событие:
подключение к СУБД и к RDP, извлечённый файл, обращение к именованному каналу, письмо.
Последний способ самый грубый: он верен для всей таблицы сразу, поэтому и стоит последним.

`app_name` из каскада убран: это имя клиентского приложения (`psql`, `SQL Developer`), а не
действие — подключение к PostgreSQL называлось именем программы, из которой пришло.

Две таблицы остаются без операции намеренно. У `flow` строка и есть сетевой поток —
`NETWORK_FLOW` для неё не пробел, а верное имя. У `telnet` в строке лежит кусок набранного
потока (`rqs.data`): вывести из него команду можно только догадкой о чужом протоколе.

### Таблица `nad_traffic_dcerpc_br`

Единственная из 38 без колонок `src` и `dst`: у её событий нет ни узла, ни адресов. Связать
такое событие с остальными можно только по `flow_id`. Подставлять узел неоткуда, и выдумывать
его нельзя — событие принимается с пустыми сущностями, а `flow_id` остаётся в `payload` как
единственная связь. Соединение по `flow_id` — вопрос к схеме сбора, а не к коннектору:
осмысленно оно только при выгрузке таблицы потоков вместе с этой.

## Безопасность: пароли в схеме

Схема содержит поле **`credentials.password`** (`keyword`) — пароли, восстановленные из незашифрованного трафика, вместе с `credentials.valid` (проверка успешности).

Это чувствительные данные, попадающие под требование ТЗ §8.7 «секреты и конфиденциальные данные не попадают в открытые логи и подсказки ИИ-модели». В коннекторе:

- пароли и ключи из трафика заменяются на маркер `[redacted]` до записи в `payload` — в хранилище кейсов, доказательный пакет и экспорт они не попадают. Маскирование идёт по имени поля и обходит вложенность и массивы: по фактическим схемам стенда (`nad_table_schemas.json`, 38 таблиц) `credentials` объявлено как `array(row("login", "valid", "password"))`, а пароли SMB и DCERPC лежат в `rqs` (`account_password`, `case_sensitive_password`, `password`), ключи сессии и шифрования — в `rqs`/`rsp`;
- сессионные cookie маскируются наравне с паролями: `cookie` объявлен в `rqs` таблицы HTTP и отдельной колонкой в RDP, `set_cookie` — в ответе HTTP. Перехваченная из трафика сессия даёт доступ без пароля, поэтому в `payload` ей места нет;
- разбор команд протоколов вскрыл носителей секрета, которых маскирование по имени поля не видело. Аргумент команды у FTP и POP3 (`PASS`), IMAP (`LOGIN`, `AUTHENTICATE`) и SMTP (`AUTH`) — это пароль или пара «логин:пароль» в base64: аргумент маскируется целиком, отделить в нём пароль от логина надёжно нельзя (пароль может содержать пробел). Сама учётная запись при этом не теряется — она уже разобрана в сущности события;
- по именам полей маскируются также `simple` (пароль простой привязки LDAP), `community`, `auth_params`, `privacy_params`, `security_parameters` (строка сообщества SNMP v1/v2c и материал аутентификации SNMPv3), `authorization` и `proxy_authorization` (базовая аутентификация HTTP). Блок `auth` в DCERPC не маскируется: по схеме это `row("type", "level")` — тип и уровень аутентификации, а не её материал;
- настройки политики паролей (`max_password_age`, `min_password_length`, `last_password_change`) не маскируются: это состояние домена, а не значения паролей;
- при ошибке разбора документа в лог пишутся только путь и номер строки, без содержимого;
- `credentials.login` сохраняется — он нужен для корреляции по учётной записи и не является секретом.

**Известная незакрытая утечка: `nad_traffic_telnet`.** Телнет передаёт сеанс открытым текстом, и в `rqs.data` попадает всё набранное, включая пароль после приглашения `Password:`. Отличить пароль от команды внутри одной строки нечем: приглашение приходит в ответе предыдущей записи, а не той же. Варианта два — маскировать `rqs.data` целиком (тогда теряются набранные команды, ради которых телнет и разбирают) или оставить как есть. Решение за заказчиком; пока поле не маскируется, и это записано здесь, а не умолчано.

Регрессия закреплена тестом `test_nad_security_password_not_in_payload_but_login_preserved` — он проверяет отсутствие пароля во всём сериализованном payload, а не только в одном поле.

**Вопрос к заказчику:** нужно ли расширить список маскируемых полей. Уже маскируются пароли, ключи сессий, сессионные cookie, пароль привязки LDAP, строка сообщества SNMP, заголовки авторизации HTTP и аргументы команд аутентификации; остаются кандидаты — `headers`, `params`, `query` и данные сеанса telnet (`rqs.data`, см. выше). Снят с рассмотрения `keypressed`: по схеме это `boolean` — признак интерактивного ввода, а не его содержимое; сеанс SSH зашифрован, и нажатий сенсор не восстанавливает. Список задаётся константой `REDACTED_FIELD_NAMES` и меняется без правки логики.

## Открытые вопросы по схеме

1. **Идентификатор документа.** В mapping нет служебного `_id` (он вне `properties`). Реализован каскад `_id` → `_ndx` → `_prn.id` → `tx_id`; какое поле фактически уникально в выгрузке — требует подтверждения на реальных данных.
2. **Выбор времени.** Присутствуют `ts`, `ts_start`, `ts_end`, `_ltime`, `tx_time`. Принято `ts` как время события; `_ltime` — предположительно время загрузки в хранилище. Требует подтверждения.
3. **Формат выгрузки.** Реализован NDJSON. Если заказчик отдаёт JSON-массив или сразу ответ `_search` целиком — потребуется дополнительный режим чтения (изменение локальное, в читателе).
4. **Остальные классы источников.** Таксономия PT SIEM получена и разобрана — [`source_schema_siem.md`](source_schema_siem.md). Схемы EDR и промышленного сенсора пока не получены; их маппинги в [`data_contract.md`](data_contract.md) остаются предположительными и подлежат такой же замене.
