# Схема источника: система сбора событий PT SIEM

Источник: файл заказчика `taxonomy.json` — таксономия PT SIEM сборки **27.0.859-release-27.0**
(собрана 2025-10-09). Это вторая **фактическая** схема, полученная от заказчика по ТЗ §6.1: до
неё маппинг класса SIEM строился на предполагаемых именах колонок (`record_id`, `device_host`,
`subject_user`, `rule_name`), которых на стенде не существует.

Файл в репозиторий не коммитится — это данные заказчика. Производные от него: этот документ,
коннектор и синтетическая фикстура.

## Состав схемы

| Параметр | Значение |
|---|---|
| Полей таксономии | 331 |
| Классы полей | `scalar` (значение), `tag` (значение из перечисления) |
| Типы | String, Number, Datetime, UUID, Bool, UUIDList и производные |
| Перечисления, важные для маппинга | `action` (80 значений), `object` (68), `status` (3), `importance` (4), `alert.ioc_type` (14), `incident.category` (34), `incident.severity` (3) |

Таксономия — это **уже нормализованная модель события**: PT SIEM разбирает исходную запись
источника сам и раскладывает её по объявленным полям. Поэтому коннектор не разбирает текст
события, а переносит объявленные поля в каноническое событие TAKT.

## Что этот класс источника даёт и чего нет в PT NAD

Главное — **цепочка процессов**: `subject.process.guid`, `subject.process.name`,
`subject.process.cmdline`, `subject.process.fullpath` и та же группа для родителя
(`subject.process.parent.*`). Признак «процесс» из ТЗ §4.2 сетевой сенсор не видит
принципиально ([`source_schema_nad.md`](source_schema_nad.md)), и закрыть его можно только
отсюда.

Кроме того, таксономия даёт то, чего в трафике нет: учётную запись с доменом и идентификатором
(`subject.account.name` / `.domain` / `.id`), результат действия (`status`: success / failure /
ongoing) и объявленную категорию инцидента, из которой выводится фаза цепочки.

## Формы записи полей

Имена полей таксономии содержат точку (`subject.account.name`). Выгрузка встречается в двух
формах записи, и коннектор читает **обе**:

- плоские ключи с точкой — `{"src.ip": "10.10.1.17"}`, так поля называет API стенда;
- вложенные объекты — `{"src": {"ip": "10.10.1.17"}}`, так выглядит экспорт в JSON.

Разбор только одной формы молча терял бы адреса и учётные записи: событие принималось бы, но в
корреляции не участвовало.

## Маппинг в каноническое событие TAKT

Реализация: [`src/takt/infrastructure/importers/siem_events.py`](../../src/takt/infrastructure/importers/siem_events.py).
Формат чтения — NDJSON, потоково. Точка входа: `python -m takt.tools.load_dataset --source pt_siem --path <файл>.ndjson`.

| Поле TAKT | Источник (приоритет сверху вниз) |
|---|---|
| `event_id` | `uuid` → составной ключ `siem:<time>\|<узел>\|<msgid>\|<src.ip>\|<dst.ip>\|<учётная запись>` |
| `observed_at` | `time` → `original_time` → `start_time` → `recv_time` |
| `source` | константа `siem` |
| `protocol` | `protocol.layer7` → `protocol` → `siem` |
| `operation` | `action` + `object` (например `LOGIN_ACCOUNT`, `START_PROCESS`) → `action` → `correlation_name` → `event_src.rule` → `msgid` → `event_type` → `SIEM_EVENT` |
| `payload_size` | `count.bytes` → `count.bytes_in + count.bytes_out` → 0 |
| `entities.host_id` | `event_src.host` → `event_src.hostname` → `event_src.fqdn` → `event_src.asset` → `src.host` → `src.hostname` |
| `entities.user_id` | `subject.account.name` → `subject.name` → `subject.account.id` |
| `entities.process_id` | `subject.process.guid` → `subject.process.id` |
| `entities.parent_process_id` | `subject.process.parent.guid` → `subject.process.parent.id` |
| `entities.src_address` | `src.ip` → `external_src.ip` → `assigned_src_ip` |
| `entities.dst_address` | `dst.ip` → `external_dst.ip` → `assigned_dst_ip` |
| `artifacts` | хеши `object.hash.*`, `subject.process.hash.*` (нижний регистр); файлы `object.fullpath`/`object.path`, `subject.process.fullpath`/`.path`; процессы `subject.process.name`, `object.process.name`; учётные записи `subject.account.name`, `object.account.name`; домены `dst.fqdn`, `external_dst.fqdn`, `event_src.fqdn`; адрес `dst.ip`; индикатор `alert.ioc_value` — типом по `alert.ioc_type` |
| `payload` | исходный документ целиком плюс фаза цепочки, если её удалось вывести |

### Три решения, которые нельзя вывести из кода без схемы

**1. Идентичность события — только `uuid`.** Поля `id` и `msgid` в таксономию входят, но
называют **тип** события в источнике (`4625` — неудачный вход), а не отдельное событие. Взяв
любое из них за идентификатор, продукт склеил бы сотни попыток подбора пароля в одно событие.
Документ без `uuid` получает составной ключ и не отбрасывается.

**2. Операция — пара «действие + объект».** Одно `action` слишком грубо: `ACCESS` одинаков для
файла и для учётной записи. Имя правила (`event_src.rule`, `correlation_name`) операцией не
является — это название срабатывания, а не то, что произошло, поэтому оно идёт запасным
вариантом. `status` в операцию не входит и остаётся в `payload`: неудачный вход — это тот же
вход, а не другое действие.

**3. Тип индикатора переводится не весь.** Перечисление `alert.ioc_type` содержит 14 значений;
артефакт получают только те, для которых в модели TAKT есть точный тип:

| `alert.ioc_type` | Тип артефакта TAKT |
|---|---|
| `domain` | `domain` |
| `hash` | `hash` |
| `host` | `host` |
| `ip_address` | `address` |
| `path` | `file` |
| `url` | `url` |
| `username` | `account` |

Остальные (`binary`, `cmdline`, `email`, `mac_address`, `meta`, `other`, `registry`) артефакта
не получают: реестровый ключ — не файл и не домен, и приписать ему ближайший тип значит соврать
о природе индикатора. Значение остаётся в `payload` и видно аналитику.

## Фаза цепочки атаки

Фазу таксономия не содержит — её нет ни одним полем. Есть объявленная **категория инцидента**
`incident.category` (34 значения), и она переводится в фазу по таблице
[`config/kill_chain/source_phases.yaml`](../../config/kill_chain/source_phases.yaml): 12
категорий переводятся, 22 объявлены непереводимыми с указанием причины. Происхождение фазы
сохраняется в событии (`attack_phase_origin`), и аналитик видит разницу между «источник сообщил
фазу» и «фаза выведена из категории источника». Основания —
[`source_phase.py`](../../src/takt/infrastructure/importers/source_phase.py) и
[`tests/test_pt_stand_phase_mapping.py`](../../tests/test_pt_stand_phase_mapping.py).

## Безопасность: полей-паролей в таксономии нет

В 331 поле таксономии нет ни одного объявленного поля пароля, ключа или токена — в отличие от
схем PT NAD, где пароли восстанавливаются из трафика. Тем не менее документы проходят то же
общее маскирование по имени поля
([`redaction.py`](../../src/takt/infrastructure/importers/redaction.py)): выгрузка несёт
свободные поля нормализатора (`datafield1`…`datafield20`) и вложенные записи, куда секрет может
попасть без объявления в схеме. Маскирование здесь — страховка, а не разбор известных полей.

Одно поле разбирается иначе — командная строка процесса, см. следующий раздел.

## Командная строка: пароль вычищается, событие остаётся

**`subject.process.cmdline`** — случай, где требование ТЗ §8.7 сталкивается с признаком
«процесс» из ТЗ §4.2. Командная строка регулярно несёт пароль
(`net use \\srv\c$ /user:CORP\svc пароль`), но по ней же видно, что запущено, с какими
ключами и над чем — ради этого класс источника и принимается. Маскирование строки целиком
закрыло бы секрет ценой самого события.

Принято промежуточное решение: из строки вычищаются **значения известных ключей передачи
пароля**, остальное сохраняется. Правила —
`CREDENTIAL_ARGUMENT_PATTERNS` в [`redaction.py`](../../src/takt/infrastructure/importers/redaction.py):

| Форма | Пример |
|---|---|
| ключ с именем пароля | `--password=X`, `/pass:X`, `-pwd X` |
| короткие ключи, отведённые под пароль | `psexec -p X`, `sqlcmd -P X`, `schtasks /rp X` |
| позиционный пароль `net user` | `net user backdoor X /add` |
| позиционный пароль `net use` | `net use \\srv\c$ /user:CORP\svc X` |
| PowerShell | `ConvertTo-SecureString "X" -AsPlainText -Force` |
| пара в одном аргументе | `curl -u svc_admin:X` |

**Маскирование заведомо неполное**, и это записано в самом модуле: способов передать пароль
аргументом больше, чем известных ключей, а позиционный пароль неизвестной программы
отличить от имени файла нечем. Правила выбраны узкими, чтобы не портить данные: `/p` в
Windows — постраничный вывод (`dir /p`), а не пароль; у `runas /user:X "cmd.exe"` в том же
месте, что у `net use`, стоит запускаемая программа; `-path` и `-port` не принимаются за
`-p`. Порча доказательства молчаливым стиранием пути хуже, чем оставленный редкий ключ.

Список ключей расширяется без правки логики. Проверка — `tests/test_importer_redaction.py`.

## Открытые вопросы по схеме

1. **Формат выгрузки.** Реализован NDJSON. Если стенд отдаёт JSON-массив или ответ API целиком —
   потребуется дополнительный режим чтения (изменение локальное, в читателе).
2. **Заполненность полей.** Таксономия объявляет 331 поле, но какие из них реально заполнены
   нормализаторами стенда — видно только на выгрузке. Каскады рассчитаны на то, что часть полей
   окажется пустой, но приоритеты внутри каскада проверяются лишь на живых данных.
3. **Корреляционные события.** У событий, порождённых правилами корреляции
   (`correlation_type = event | incident`), состав полей отличается от нормализованных: у них
   может не быть `action`. Каскад операции это учитывает, но на данных не проверен.
4. **Учётная запись без домена.** В `user_id` идёт `subject.account.name` без домена — так она
   склеивается с логином из сетевого сенсора, где домена нет. Если на стенде одинаковые имена
   встречаются в разных доменах, ключ склейки придётся расширить до `домен\имя`.
