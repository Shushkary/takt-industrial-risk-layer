# Окно расследования: запуск на четырёх источниках

Воспроизводимый прогон демонстрационного сценария INC-002 от загрузки данных до окна
аналитика. Все числа ниже — результат прогона, а не ожидание.

## 1. Загрузка четырёх источников

Хранилище обязано быть постоянным: загрузчик и API — разные процессы, при хранилище
в памяти загруженное некому передать.

```powershell
$env:TAKT_STORAGE = "sqlite"; $env:PYTHONPATH = "src"; $env:PYTHONUTF8 = "1"
python -m takt.tools.load_dataset --source edr     --path tests/fixtures/pt_techlab/inc_002/edr.csv
python -m takt.tools.load_dataset --source siem    --path tests/fixtures/pt_techlab/inc_002/siem.csv
python -m takt.tools.load_dataset --source netflow --path tests/fixtures/pt_techlab/inc_002/ndr.csv
python -m takt.tools.load_dataset --source ot      --path tests/fixtures/pt_techlab/inc_002/ot.csv
```

Принято 1030 событий: EDR 531, SIEM 240, Netflow 227, OT 32.

Источник `netflow` читает тот же файл потоков, что и `ndr`, но как поток без вердикта
средства обнаружения: строка приводится к полям интеграции (`flow_src_ip`, `flow_dst_ip`,
`flow_bytes`) и проходит тот же нормализатор, что и приём через
`POST /integrations/ingest/netflow`.

Выгрузка сетевого сенсора PT NAD приходит не CSV, а построчным NDJSON — по одному
JSON-объекту на строку, как в ответе `_search`/`scroll`. Для неё отдельный источник:

```powershell
python -m takt.tools.load_dataset --source nad --path <выгрузка>.ndjson
```

События из этой выгрузки попадают в класс `ndr`. Поле `credentials.password` схемы NAD
содержит пароли, восстановленные из трафика: коннектор заменяет его маркером до записи
в `payload` — см. [source_schema_nad.md](source_schema_nad.md). Битая строка загрузку не
останавливает и журналируется без содержимого документа.

Имя источника в команде называет **формат выгрузки**, а не класс события: `nad` приходит
в `ndr`, `netflow` — в `network_events`. Настроенное доверие берётся по классу события.

## 2. Сборка инцидента

```powershell
python -m takt.tools.assemble_incident --case-id INC-002 `
  --seed user:smirnov --seed user:svc_build --seed address:185.220.101.34 `
  --seed artifact:domain:cdn-metrics.example-analytics.com `
  --seed host:artifact:app-setup.msi --seed host:pipeline:release-prod `
  --expand-host ws-17 --expand-host build-srv-01 `
  --title "Компрометация конвейера сборки: фишинг, C2, подмена артефакта"
```

Результат: ядро 25 событий по отличительным сущностям, расширение до уровня узла
добирает 16, итого 41.

С 2026-09-03 первый шаг (сборка ядра по отличительным сущностям дел со сработавшим
инвариантом) выполняется сам — конвейером приёма, по каждому срабатыванию инварианта, без
команды аналитика и без заранее названных сущностей. Команда выше нужна, только когда сиды
известны заранее и требуется собрать инцидент по ним. Повторить шаг с другим порогом
отличительности — `POST /cases/assemble/auto` или кнопка «Собрать инциденты» в очереди АРМ.
Второй шаг (расширение до уровня узла) автоматика намеренно не делает: узел добирает
штатную активность вместе с недостающими событиями, и это остаётся решением аналитика.
Из АРМ он доступен на карточке собранного инцидента, блок «Расширение до узла»: список
узлов строится по текущему составу дела, отмеченный узел уже расширен. Действие вызывает
тот же `POST /cases/assemble/pivot` с теми же сидами (читаются из `case.artifacts` с
`source: pivot-seed`) и выбранными `expand_hosts` — не новый механизм, а прежний,
дотянутый до интерфейса.

Три отвлекающие аномалии датасета собираются отдельными делами — на них проверяется отсев
ложных срабатываний, и очередь перестаёт быть однородной лентой одиночных срабатываний:

```powershell
python -m takt.tools.assemble_incident --case-id INC-003 --seed user:admin_ops `
  --title "Администрирование вне смены: admin_ops на 12 рабочих станциях"
python -m takt.tools.assemble_incident --case-id INC-004 --seed host:scan-01 `
  --title "Сканирование сети с узла scan-01"
python -m takt.tools.assemble_incident --case-id INC-005 --seed host:backup-01 --seed user:svc_backup `
  --title "Ночной бэкап: всплеск SMB-трафика с backup-01"
```

## 3. Backend и АРМ

Две команды, по одной на окно терминала. Backend:

```powershell
python -m uvicorn takt.interface_adapters.api.main:app --host 127.0.0.1 --port 8090
```

Аутентификация продукта включена по умолчанию (`TAKT_AUTH_REQUIRED`), и рабочее место с
версии P2 умеет предъявлять ключ. Чтобы на стенде были видны роль и автор действий в журнале,
backend поднимают с именованными ключами:

```powershell
$env:TAKT_AUTH_REQUIRED = "1"
$env:TAKT_API_KEYS = "key-l2:smirnov.analyst:analyst_l2,key-mgr:orlov.head:manager"
```

Ключ вводится в шапке АРМ и хранится в браузере. Без ключа вкладка показывает «требуется ключ
доступа» и сама открывает поле ввода — это не сбой связи. С `key-mgr` (роль только на чтение)
действия правки состава, находок, статуса и пакета реагирования скрыты, а не отвечают отказом
после нажатия.

АРМ:

```powershell
python -m scripts.serve_pt_arm
```

`serve_pt_arm` раздаёт `frontend/takt-pt-arm` на `127.0.0.1:8091` и проксирует `/api/*` на
backend, снимая префикс: локальный backend поднят без него. Каталог, порт и адрес backend
меняются ключами `--root`, `--port`, `--api-base`. Если backend не поднят, АРМ получает
`502 backend_unreachable`, а не зависает. Скрипт отказывается стартовать, когда в каталоге нет
`app.min.js`: `index.html` подключает сборку, а не исходник.

На боевом контуре статику раздаёт nginx (`nginx.takt-pt-arm.conf`): там АРМ живёт на подпути
`/takt_pt_arm/`, а `/takt_pt_arm/api/` проксируется на backend с префиксом `/api`. Адрес API
можно переопределить, задав `window.TAKT_API_BASE` до загрузки `app.min.js`.

Оба процесса живут ровно столько, сколько открыт терминал: стенд поднимается из репозитория
по этим двум командам, а не восстанавливается по памяти.

После правки `app.js` или `styles.css` обязательна пересборка `node build-production.mjs`
и подъём параметра `?v=` в `index.html` и `app.js`.

## Что показывает окно

| Блок | Источник данных |
|---|---|
| Очередь инцидентов | `GET /cases`, порядок: балл риска, при равенстве — число событий |
| Сводка, инварианты, находки | `GET /cases/{id}/workspace`, поле `case` |
| Состав по источникам | те же события, сгруппированные по `source` |
| Цепочка событий | `events`, по возрастанию `observed_at`, время в UTC |
| Связи сущностей | `graph.edges` |
| Варианты реагирования | артефакты кейса с `source = pivot-seed` |
| Карточка сущности | `GET /entities/{type}/{id}/card` |
| Кто работает и что ему доступно | `GET /session` (`actor_id`, роль, `permissions`) |
| Сведённая очередь | `GET /cases/groups`, разрезы `asset` и `operation` |
| Правка состава дела | `POST .../detach`, `.../events/attach`, `.../merge`, `.../split` |
| Приложенные документы | `POST /cases/{id}/manual-permits` |
| Выходные документы | `GET /cases/{id}/export.pdf`, `.../decision-brief.pdf` |
| Конфигурация: веса оценки риска | `GET /config/risk-weights`, `PUT /config/risk-weights` (роль `admin`) |

Читаемость окна закрыта отдельной правкой (аудит интерфейса, 4 сентября 2026):

- **Очередь** собирается из полей продукта, а не из заголовка: класс риска показан полем и
  цветом, код операции — моноширинным, рядом актив и число событий. Заголовок конвейера
  приёма («[x35] Риск низкий: …») дублировал класс и число, и слева у каждой строки стояло
  одно и то же слово «Риск».
- **Цепочка событий** сворачивает серию одинаковых событий в строку со счётчиком: события
  остаются в таблице и раскрываются по требованию, потому что отцепить нужно конкретное
  событие. Колонка, пустая во всех показанных событиях, скрывается.
- **Одно слово на одну сущность.** В окне везде «инцидент»; «дело» и «кейс» остались в
  документации и в именах полей API.
- **Журнал** сокращает контрольные суммы и идентификаторы улик до восьми знаков с копированием
  полного значения. Формулировки записей не трогаются: часть из них продукт ищет по точному
  тексту (`ASSEMBLY_MARKER`, отчёт соответствия).
- **Шапка** разделена на три группы: справка, доступ и настройки, состояние.
- **Порог редкости сущности** (прежде «порог отличительности») переехал из панели очереди в
  окно «Конфиг»: правят его раз в несколько смен, а место занимал всю смену.

У каждого блока и каждого ключевого значения есть кнопка пояснения: что это, откуда
берётся и что с этим делать. Реестр пояснений — константа `HELP` в `app.js`, 60 записей, из
них 50 со ссылкой на документ-источник. Запись имеет вид `{title, what, source, action, doc}`
и рисуется подзаголовками «Что это · Откуда · Что делать»; при наведении на «?» показывается
первое предложение.

### Сверка с ТЗ §5: где объяснена каждая функция

Функциональный контур ТЗ «Техлаб 2026» проверен против реестра пояснений — не «есть ли
функция», а «объяснена ли она там, где ею пользуются».

| Функция ТЗ §5 | Пояснение в окне |
|---|---|
| Единый рабочий стол инцидента | `summary`, `chain`, `event_count` |
| Подключение источников (≥ 4 классов) | `sources`, `source` |
| Корреляция событий, ручная корректировка связей | `xai`, `evidence`, `relink`, `queue_groups` |
| Граф / таймлайн расследования | `graph`, `reconstruction`, `attack_graph`, `time_utc` |
| Карточка сущности | `entity`, `entity_host`, `entity_user`, `entity_address` |
| Журнал находок | `findings`, `artifact` |
| Обогащение артефактов | **не показывается в окне**: разбор значения снят вместе с вкладкой поиска, маршрут `POST /enrichment/decode` остаётся в API |
| Поиск и фильтрация | `queue_filters`; поиск по событиям снят с окна, маршрут `GET /events/search` остаётся в API и используется при прицеплении события к делу |
| Подсказки следующих шагов | **не реализовано**; сказано прямо в `assistant` |
| ИИ-ассистент (опция) | `lm` |
| Подготовка пакета реагирования | `response`, `sim_summary` |
| Отчёт по инциденту | `report`, `verdict` |
| Роли и права доступа | **`access`** |
| Журнал действий | `journal`, `counter_takt` |

Три записи добавлены этой сверкой (выделены). Два пункта закрыты не полностью, и оба названы
в интерфейсе, а не умолчаны:

- **Репутация адресов и хешей, вердикт песочницы.** Внешние проверки: каждая выносит признак
  инцидента за периметр, поэтому требует согласованной интеграции и разрешённого списка
  адресатов. В поставке их нет. Разбор закодированного значения выполняет маршрут
  `POST /enrichment/decode`; из окна он снят вместе с вкладкой поиска.
- **Подсказки следующих шагов.** Конвейер называет, чего не хватает для вывода (маршрут
  добора контекста), но типовых действий расследования не предлагает.

### Как меняются правила

Вопрос «как у вас происходит дообучение» на демонстрации звучит раньше остальных. Ответ —
кнопка «как меняются правила» в блоке сработавших инвариантов: обучаемой модели в контуре
вердикта нет, меняются правила и конфигурация, и цикл на каждом обороте проходит через
человека.

Пять шагов: разметка дела статусом → сведение разметки по правилам
(`GET /analytics/invariant-feedback`) → предложение продукта с именем правила → правка
человеком в `config/invariants/*.yaml` или `config/risk_weights.yaml` → повторный прогон с
оценкой качества детектирования и бэктестом.

Четвёртый шаг доступен и из окна: кнопка «конфиг» в шапке (роль `admin`) открывает веса
факторов и пороги классов риска. Это тот же файл и та же метка версии, а не второй набор
весов: сумма весов держится равной единице, версия поднимается при каждой записи, причина
уходит в журнал безопасности. Уже собранные дела не пересчитываются — новый набор действует
на последующие.

Автоматического пересчёта нет намеренно: он сделал бы вердикт зависящим от момента расчёта,
и повторный прогон того же дела на той же версии кода дал бы другой результат — доказательный
пакет перестал бы быть воспроизводимым. Обучение здесь — это **версия конфигурации**, а не
состояние модели, и по любому вердикту видно, какими правилами он получен.

### Алгоритм разбора

Кнопка «алгоритм разбора» в шапке рабочего места открывает пояснение, отвечающее на вопрос
«где у вас машинный ассистент». Ответ: то, что в других продуктах делает ассистент, здесь
выполняет детерминированный конвейер, и он разложен на одиннадцать шагов — приём и приведение
к одной модели, обогащение, оценка риска, проверка инвариантов, сведение однотипного, сборка
дела пивотом с расширением до узла, сверка с организационным контекстом, триадный вердикт,
контрфактическое объяснение с маршрутом добора, обоснованность и пакет реагирования вместе с
контуром целостности. Обоснованность считается продуктом и уходит в отчёты; в окне она не
показывается — на вкладке расследования стоит вердикт и перечень «Чего не хватает».

Порядок здесь и есть содержание: по нему аналитик находит шаг, на котором расходится с
выводом продукта, — состав дела правится на шаге сборки, неопределённость снимается на шаге
сверки, ошибка правила видна на шаге инвариантов. Поэтому шаги подаются нумерованным списком
(поле `steps` записи реестра, стиль `.modal-steps`), а не абзацем: цифры внутри абзаца
разъезжаются при переносе и не читаются экранным диктором как порядок.

Роль языковой модели описана отдельно — кнопка «Роль языковой модели» на вкладке
«Симуляция», см. [simulation.md](simulation.md).

### Ручные действия

| Показатель | Значение |
|---|---|
| Действий в ТАКТ (замер по журналу кейса) | 9 |
| Действий в текущем процессе (расчёт по модели) | 88 |
| Сокращение | 89.8% |

Замер стороны ТАКТ — из append-only журнала `case_audit_ledger`; сторона текущего процесса
рассчитана по модели с явными коэффициентами. Время не считается: коэффициента «секунд на
действие» никто не измерял. Границы применимости и порядок подстановки наблюдённых значений —
[baseline_methodology.md](baseline_methodology.md), раздел «Расчёт по INC-002».

Воспроизведение: `python -m scripts.eval_baseline_inc002 --case-id INC-002`.

Класс `MEDIUM` при балле 0.626 — состояние после того, как из `combine_risk` снят множитель
качества данных (решение владельца 2026-08-24). Качество влияет одним каналом — своим
взвешенным вектором, потолок шкалы вернулся к 1.000, пороги откачены к 0.85 / 0.65 / 0.40.
Балл INC-002 при этом вырос (0.536 → 0.626), но порог «высокого» вырос сильнее: до порога
0.65 не хватает 0.024.

**Высокого класса в очереди прогона нет ни одного** — владелец принял это осознанно, зная,
что раньше требовал видеть в очереди три класса. Занижать порог под конкретный кейс не стали:
`docs/product_boundary.md` запрещает числовые характеристики без ссылки на измерение, а 0.626
— это 63% шкалы, то есть модель на этом корпусе действительно не выдаёт «высокого». Разбор и
замеры — [risk_scale_calibration.md](../risk_scale_calibration.md), раздел
«Продолжение 2026-08-24: снятие множителя качества».

## Дефекты, найденные этой проверкой

Все исправлены, на каждый есть регрессия.

| Что было | Следствие |
|---|---|
