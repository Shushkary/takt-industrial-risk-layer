# Промпты по спринтам с чек-листами

Ниже — план из 6 спринтов, каждый по 2 недели. Промпты сформулированы так, чтобы их можно было передать инженеру или агенту-кодеру (например, Claude Code) с минимальными правками. Внутри каждого спринта — цель, входные допущения, промпт-задача и чек-лист приёмки (Definition of Done).

## Спринт 1. Безопасность периметра (P0)

**Цель.** Закрыть критические дыры в HTTP-периметре и SIEM-интеграции до того, как продукт выйдет за пределы лаборатории.

**Входные допущения.** Кодовая база v0.6.23, FastAPI + middleware-стек уже на месте.

### Промпт

> Ты работаешь в корне этого репозитория, ветка `release/0.6.x`. Внеси изменения в L3/L4 без затрагивания L1 Domain. Реализуй три блока:
>
> 1. **Жёсткая аутентификация для write-эндпоинтов.** Введи режим `TAKT_AUTH_REQUIRED` со значением по умолчанию `true`. При `true` все маршруты, кроме `/live`, `/ready`, `/health`, `/metrics`, `/docs`, `/redoc`, `/openapi.json`, требуют корректный `X-TAKT-API-Key`. Запуск без секрета в этом режиме завершается ошибкой на старте (fail-closed). Добавь в `/health` поле `auth.mode` со значением `required`/`optional`/`disabled`.
> 2. **Безопасный SIEM allowlist.** Замени префиксное сравнение в `siem_webhook.allowed_url_prefixes` на структурный матчинг разобранного URL: точное совпадение хоста или суффикс с разделителем `.`, белый список схем (`https` обязательно в проде), запрет `userinfo` и нестандартных портов вне whitelist. Добавь DNS-rebinding mitigation: резолв хоста при отправке, проверка, что результирующий IP не в RFC1918/loopback/link-local (если только профиль не `dev`), повторное использование того же IP при ретраях.
> 3. **Защита от подмены клиентского IP в rate limiter.** Введи список `TAKT_TRUSTED_PROXIES` (CIDR). Заголовок из `TAKT_RATE_LIMIT_IP_HEADER` учитывается только если запрос пришёл с доверенного upstream; при цепочке берётся последний не-доверенный hop. По умолчанию список пуст, и заголовок игнорируется.
>
> Все изменения покрой unit- и integration-тестами. Обнови README раздел «Security» и `docs/product_boundary.md`. Не ломай контракт публичных эндпоинтов.

### Чек-лист приёмки

- [ ] `TAKT_AUTH_REQUIRED=true` по умолчанию; запуск без `TAKT_API_KEY` падает с понятным сообщением
- [ ] Все mutating-роуты возвращают 401 без ключа; публичные пути по-прежнему доступны без него
- [ ] Тест: `https://siem.internal.corp.attacker.com` отклоняется при allowlist `https://siem.internal.corp`
- [ ] Тест: webhook на хост, который резолвится в `127.0.0.1`/`10.0.0.0/8`, отклоняется в профиле `prod`
- [ ] Тест: повторный запрос идёт на тот же IP, что и первый (нет re-resolve между ретраями)
- [ ] Rate limiter игнорирует `X-Forwarded-For` от недоверенного источника
- [ ] `/health` показывает `auth.mode`, `siem.allowlist_mode`, `proxy.trusted_count`
- [ ] Регрессий по существующим тестам нет; покрытие L4 не упало
- [ ] CHANGELOG отмечает breaking change для оператора (требуется выставить переменные окружения)

## Спринт 2. Модель кейса и слияние (P0)

**Цель.** Перестроить логику `burst_fingerprint` и слияния так, чтобы атакующий не мог «прятаться» в склеенном кейсе и чтобы один физический инцидент не расщеплялся по источникам.

### Промпт

> Внеси изменения в L1 Domain (модель кейса, движок слияния) и в L2 (use-case `ProcessEventUseCase`).
>
> 1. **Расширь `burst_fingerprint`** до композиции `source | asset_id | operation | time_bucket(event_ts, bucket_sec)`, где `bucket_sec` берётся из `risk_weights.yaml` (`alert_fatigue.bucket_sec`, дефолт 300). Старое поведение оставь как режим `legacy` для обратной совместимости в backtest.
> 2. **Сохраняй полный журнал срабатываний при слиянии.** В кейсе заведи `invariant_hits: list[InvariantHit]` с полями `invariant_id`, `event_ref`, `ts`, `score_contribution`, `dq_snapshot`. Поле `risk_score` остаётся максимумом, но не вытесняет историю.
> 3. **Перейди на модель «один инцидент — один кейс, источники — наблюдения».** Сними правило «разные source → разные кейсы». Введи в кейсе коллекцию `observations: list[Observation]` с `source`, `ingest_trust`, `event_ids`. При агрегации `risk_score` используй `ingest_trust` как вес наблюдения, а не как ключ расщепления.
> 4. **Унеси `alert_fatigue_guard` из каталога 26 инвариантов** в L2-пайплайн дедупликации. Каталог станет содержать 25 доменных инвариантов; обнови `GET /invariants` и тесты.
>
> Обеспечь миграцию данных: для существующих SQLite-баз — скрипт `scripts/migrate_0_7_0.py`, который сворачивает кейсы с одинаковой парой `(asset_id, operation)` и пересекающимися окнами в один кейс с массивом наблюдений.

### Чек-лист приёмки

- [x] `risk_weights.yaml` содержит секцию `alert_fatigue` с `bucket_sec` и `mode: legacy|bucketed`
- [x] Property-based тест: при перестановке порядка событий в одном бакете итоговый `risk_score` и набор `invariant_hits` инвариантны
- [x] Тест: атака, имитирующая совпадение `source|asset|operation` в течение 10 минут с интервалом 11 минут, создаёт **два** кейса (а не один склеенный)
- [x] Тест: события из IDS и из журнала ПЛК на один актив и одну операцию попадают в один кейс с двумя `observations`
- [x] `GET /invariants` отдаёт столько записей, сколько значений в `InvariantId` (сейчас **26**; после удаления `alert_fatigue_guard` добавлен доменный `polling_period_doubling_suspect`); `alert_fatigue_guard` отсутствует в enum/API
- [x] `GET /cases/{id}` показывает `invariant_hits` с временными метками и не теряет ни одного срабатывания при слиянии
- [x] Скрипт миграции идемпотентен: повторный запуск не порождает дубли
- [x] Backtest на `plc_polling_demo.csv` в режиме `legacy` даёт прежний результат byte-to-byte

## Спринт 3. Доменная чистота и декларативные инварианты (P1)

**Цель.** Убрать скрытые зависимости от системных вызовов, формализовать сомнительный `polling_chaos_feigenbaum`, перевести правила инвариантов в данные.

### Промпт

> Работаешь в L1 Domain и L4 Infrastructure. L2 трогаешь только в части DI.
>
> 1. **Введи порты `SystemClock` и `IdProvider`** в `domain/ports/`. Все вызовы `datetime.utcnow()`, `time.time()`, `uuid.uuid4()` в домене и use-case-ах замени на эти порты. В L4 предоставь реализации `RealClock`, `RealIdProvider`. Для тестов — `FrozenClock`, `SequentialIdProvider`.
> 2. **Переведи каталог инвариантов в декларативный YAML.** Создай `config/invariants/*.yaml` с полями `id`, `block_key`, `title`, `inputs` (какие фичи событий нужны), `window` (глубина истории, в событиях или секундах), `predicate` (DSL-выражение или ссылка на встроенную функцию), `severity_curve`. Движок `invariants/evaluator` исполняет правила из этих файлов; pydantic-схема валидирует загрузку при старте.
> 3. **Реши судьбу `polling_chaos_feigenbaum`.** Выбери один из двух путей и зафиксируй в `docs/feigenbaum_rationale.md`:
>    - формализация: укажи отображение, способ оценки последовательных перепадов, статистический критерий (например, тест Колмогорова — Смирнова на распределение отношений), целевой FPR на эталонной выборке без атак;
>    - переименование: смени `id` на `polling_period_doubling_suspect`, убери из публичных материалов любые упоминания «δ Фейгенбаума» как закона.
>    Без выбора и доказательной базы инвариант помечается `experimental: true` и не участвует в агрегации `risk_score` по умолчанию.
> 4. **Параметризуй глубину контекста** в L2: каждый инвариант декларирует `window`, оркестратор формирует контекст ровно нужного размера, а не «последние 5».

### Чек-лист приёмки

- [x] В **`takt.domain`** нет прямых вызовов **`datetime.now`/`utcnow`**, **`time.time`**, **`uuid4`** (тест **`tests/test_domain_ast_policy.py`**; *замечание:* в домене по-прежнему допустимы тип **`datetime`** и импорт модуля **`datetime`**, запрет только на перечисленные вызовы*)
- [x] **`import-linter`**: L1 не тянет L4 (контракт в **`pyproject.toml`**)
- [x] **`config/invariants/*.yaml`**: по одному файлу на каждый **`InvariantId`** (сейчас **26** файлов, не 25); загрузка через Pydantic при старте API (**`load_invariant_catalog_from_dir`**)
- [x] Изменение порога в YAML меняет поведение без правки Python: **`tests/test_invariant_catalog_yaml.py`** (**`brute_force` → `params.auth_fail_threshold`**)
- [x] **`docs/feigenbaum_rationale.md`**: зафиксирован путь **переименования** (**`polling_period_doubling_suspect`**, без «закона δ» в публичных формулировках)
- [x] Условие про **`experimental`**: при **`experimental: true`** в YAML и профиле без **`include_experimental_invariants`** правило не попадает в **`invariant_hits`** и не усиливает rhythm из chaos (**`tests/test_assess_flow.py`**, **`AssessRiskUseCase` + каталог**). Путь «только переименование» без флага experimental оставляет вклад в score по умолчанию — это согласовано с документом
- [~] **Контекст `brute_force` ≥ 20 событий**: окно **`auth_fail_window`** и срез **`recent[-window:]`** в **`evaluator`** покрыты тестами (**`tests/test_invariants_evaluator.py`**); глубина буфера L2 задаётся **`max(5, auth_fail_window, max context_window_events)`** — для дефолтного конфига **≥ 20**; отдельного интеграционного теста «ровно столько событий передаётся в **`collect_extended_invariants`**» нет

## Спринт 4. Хранилище, миграции, идемпотентность (P1)

**Цель.** Сделать персистентный слой пригодным к боевой эксплуатации.

### Промпт

> Работаешь в L4 Infrastructure и в API-уровне L3.
>
> 1. **Миграции.** Заведи каталог `migrations/` с файлами вида `0001_init.sql`, `0002_observations.sql`. Реализуй раннер, который читает `app_metadata.schema_version` и применяет недостающие миграции в транзакции. Стартап приложения должен падать, если миграции расходятся со схемой.
> 2. **Бэкап.** Добавь команду `python -m takt.tools.backup --output <path>`, использующую `sqlite3.Connection.backup()`. Добавь README-раздел «Backup & Restore».
> 3. **Идемпотентный ingest.** Принимай заголовок `Idempotency-Key` в `POST /events` и `POST /events/batch`. Кеш ключей живёт в SQLite-таблице `idempotency_keys` с TTL (по умолчанию 24 ч). Повторный запрос с тем же ключом и тем же телом возвращает закешированный ответ; с другим телом — 409.
> 4. **Подпись и аудит импорта.** `POST /cases/import/full.json` требует `X-TAKT-Import-Signature` (HMAC-SHA256 от тела на серверном секрете `TAKT_IMPORT_HMAC_SECRET`). Каждое использование импорта пишется в append-only таблицу `audit_log` с `actor`, `ts`, `bytes`, `cases_count`, `request_id`.
> 5. **Конкурентность event window.** Перенеси «окно последних 64 событий» из process-local памяти в общий слой: либо отдельная таблица `recent_events` с TTL, либо явное ограничение `--workers 1` в Dockerfile. Зафиксируй выбор в документации.

### Чек-лист приёмки

- [ ] Холодный старт на пустой БД проходит миграции до актуальной `schema_version`
- [ ] Старт на БД с будущей `schema_version` (откат версии приложения) падает с понятным сообщением
- [ ] `backup` создаёт целостный файл, который открывается отдельным экземпляром sqlite

- [ ] При запуске с `--workers 2` (если выбран shared-режим) окно событий консистентно между воркерами; иначе Dockerfile форсит 1 воркер и это задокументировано

## Спринт 6. Качество, регрессии, релизный гейт (P2)

**Цель.** Зафиксировать достигнутое качество и не дать ему деградировать.

### Промпт

> 1. **Property-based тесты.** Используя Hypothesis, покрой:
>    - монотонность `risk_engine` по каждому фактору;
>    - коммутативность слияния в пределах одного `time_bucket`;
>    - инвариант «ухудшение качества данных повышает `risk_score` не более чем на вес вектора
>      качества» (формулировка изменена 2026-08-24 — см. примечание после промпта);
>    - устойчивость парсера событий к мусорным полям.
> 2. **Регрессионный backtest.** Закрепи в `tests/regression/` ожидаемый JSON-результат прогона `plc_polling_demo.csv` при дефолтной конфигурации. Тест сравнивает поэлементно `case_id`, `risk_score`, `risk_class`, отсортированный список `invariant_hits`. Любое изменение требует осознанного обновления фикстуры с пометкой в CHANGELOG.
> 3. **JSON Schema на YAML-конфиги.** Сгенерируй pydantic-модели для `risk_weights.yaml` и `config/invariants/*.yaml`. CI-тест валидирует все примеры в репозитории.
> 4. **Mutation testing.** Подключи `mutmut` к `src/takt/domain/`. В CI: пороговое значение mutation score ≥ 70 % на старте, цель — 85 %.
> 5. **Fuzzing API.** Подключи `schemathesis` к `/openapi.json`, прогоняй в CI как отдельную job на 5 минут. Допустимы только 4xx/5xx с корректной структурой `MiddlewareErrorJson`; падения по `500` без `request_id` — провал сборки.
> 6. **Релизный гейт.** Заведи документ `docs/release_checklist.md`, который перечисляет: пройденные миграции, актуальный SBOM, отсутствие критических CVE, актуальные результаты backtest, версию схемы инвариантов, факт ревью изменений в `risk_weights.yaml`.

**Примечание 2026-08-24: знак влияния качества данных сменён намеренно.**

Исходно пункт 1 требовал свойства «снижение `data_quality` не повышает `risk_score` без новых
срабатываний». Оно держалось не замыслом модели, а множителем `dq_factor` в `combine_risk`:
итог умножался на `dq_score`, поэтому испорченные данные балл понижали. Тот же `dq_score`
одновременно поднимал вектор `data_quality` (вызывающие задают его как `1 − dq_score`) —
одно измерение входило в оценку дважды и в противоположных направлениях, а вес вектора
качества (0.20) нельзя было «получить» ни при каком наборе признаков.

Множитель снят решением владельца 2026-08-24; качество данных влияет одним каналом — своим
взвешенным вектором. Ухудшение данных теперь балл **повышает**: потеря видимости считается
признаком риска, а не поводом смягчить разбор. Смена знака подтверждена владельцем как
намеренная. Property-тестом прежнее свойство закреплено не было — в
`tests/test_risk_engine_properties.py` есть только монотонность по осям `breakdown`, она
правку переживает. Разбор и замеры — [`risk_scale_calibration.md`](risk_scale_calibration.md),
раздел «Продолжение 2026-08-24: снятие множителя качества».
