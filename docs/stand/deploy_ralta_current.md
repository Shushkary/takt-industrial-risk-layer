# Промпт для агента: выкладка АРМ ТАКТ на ВМ ralta.ru

Скопируйте текст ниже целиком и передайте агенту-исполнителю.

---

Ты выкладываешь два фронтенда на боевую ВМ. Работай аккуратно: на этой же машине живут другие сайты, их трогать нельзя.

## Доступ

```
ssh -i ~/.ssh/id_rsa_spaceweb torionadmin@89.111.142.231
```

Пользователь `torionadmin` имеет sudo без пароля. Домен `ralta.ru` указывает на этот же адрес (89.111.142.231).

|---|---|---|---|

| React-АРМ | `D:\TAKT\TAKT PT\Version_3\app\frontend\takt-arm\dist` | каталог `takt_pt` в корне сайта ralta.ru | https://ralta.ru/takt_pt/ |

Основным интерфейсом выбран **takt_pt_arm**. React-вариант выкладывается как вспомогательный.

## Состояние на 2026-08-03 (проверено снаружи)

Перед выкладкой учти результаты внешней диагностики:

| Проверка | Результат |
|---|---|
| `https://torion.shop/`, `https://torion.su/` | **200** — ВМ жива, nginx работает |
| `http://ralta.ru/`, `https://ralta.ru/` | **нет ответа** (соединение установлено, HTTP-ответа нет) |
| `https://ralta.ru/takt_pt_arm/`, `/takt_pt/` | нет ответа |
| Порт 22 (SSH) | не отвечает, TCP-таймаут |
| Порты 80 / 443 | принимают соединения |
| DNS | `ralta.ru`, `torion.shop`, `torion.su` → все на `89.111.142.231` |

Из этого следует два вывода:

1. **Машина работает** — соседние сайты на том же адресе отдают 200. Недоступен именно SSH, это отдельная проблема доступа, а не падение сервера.
2. **Сайт `ralta.ru` сейчас не обслуживается.** Соединение на порт 80/443 проходит, но HTTP-ответа нет, тогда как `torion.shop` на том же адресе отвечает штатно. Наиболее вероятно, что для `ralta.ru` **нет рабочего server-блока nginx** (либо запросы отбрасываются default-сервером, например через `return 444`).

Поэтому задача, скорее всего, **шире простого копирования файлов**: может потребоваться создать vhost для `ralta.ru` и выпустить для него TLS-сертификат. Проверь это в разведке и сообщи до изменений.

## Восстановление SSH (предусловие)

Выкладка невозможна, пока порт 22 не отвечает. Что стоит проверить владельцу:

- панель управления SpaceWeb — консоль VM (VNC/KVM) даёт доступ в обход SSH;
- правила фаервола провайдера и локального (`ufw`/`iptables`) — не закрыт ли 22;
- `fail2ban` — не забанен ли текущий внешний IP после серии подключений;
- работает ли служба: `systemctl status ssh` (через консоль провайдера).

Не пытайся обходить блокировку доступа техническими средствами — дождись, пока владелец восстановит SSH штатным способом.

## Шаг 0. Разведка перед любыми изменениями

Ничего не меняй, пока не выяснишь фактическое состояние:

0. **Есть ли вообще server-блок для `ralta.ru`** (см. раздел выше — снаружи сайт не отвечает):
   `grep -rn 'ralta' /etc/nginx/` и `sudo nginx -T | grep -n -A5 'server_name.*ralta'`.
   Если блока нет — это и есть причина недоступности; не выкладывай молча, сначала согласуй создание vhost (включая TLS-сертификат) и покажи предлагаемый конфиг.
   Если блок есть — выясни, почему нет ответа: `sudo nginx -T | head -40` (какой сервер default), логи `/var/log/nginx/error.log`, слушает ли nginx нужные адреса (`sudo ss -lntp | grep nginx`).
1. Корень сайта ralta.ru в nginx (ожидается `/var/www/ralta`, но проверь: `grep -rn 'ralta' /etc/nginx/sites-enabled/ /etc/nginx/sites-available/`).
2. Существуют ли уже каталоги `takt_pt_arm` и `takt_pt`, что в них лежит.
3. **Какой файл служит точкой входа АРМ.** В исходниках есть два варианта: `index.html` (подключает внешний `styles.css`) и `index.prod.html` (стили вшиты внутрь). Сравни развёрнутый `index.html` с обоими локальными файлами и **сохрани ту же схему**, что уже применена на сервере. Если на сервере лежит сборка с вшитыми стилями — значит при выкладке `index.prod.html` переименовывают в `index.html`.
4. Отвечает ли бэкенд АРМ: `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:18092/health`.

Результаты разведки покажи до продолжения.

## Шаг 1. Резервные копии

На этом сервере принята схема бэкапов с меткой времени — сохрани её:

```bash
STAMP=$(date -u +%Y%m%dT%H%M%SZ)
sudo cp -a <корень>/takt_pt_arm <корень>/takt_pt_arm.pre-verdict-$STAMP
sudo cp -a <корень>/takt_pt      <корень>/takt_pt.pre-base-$STAMP
```

Запиши точные имена бэкапов — они понадобятся для отката.

## Шаг 2. Выкладка АРМ (takt_pt_arm)

Копируй **все** файлы из `D:\TAKT\TAKT PT\takt_pt_arm`, включая:

- `index.html`, `app.min.js`, `styles.css`, `styles.min.css`
- `index.prod.html`
- **`.gz`-файлы: `app.min.js.gz`, `index.prod.html.gz`, `styles.css.gz`**

**Критично про `.gz`.** В nginx включён `gzip_static on` — он отдаёт `app.min.js.gz` вместо `app.min.js`, если файл существует. Если залить новый `app.min.js`, но оставить старый `.gz`, пользователи получат **старый код**, и внешне это выглядит как «изменения не применились». Заливай `.gz` одновременно с исходниками либо удаляй устаревшие `.gz` на сервере.

Исходники `app.js` и `build-production.mjs` на сервер класть не нужно — только собранные артефакты и `index.html`/`styles.css`.

Версия для сброса кэша в этой сборке — `v=20260803-03` (проставлена в `index.html` и `app.min.js`).

## Шаг 3. Выкладка React-АРМ (takt_pt)

Содержимое локального `dist` (там `index.html`, `assets/`, `vite.svg`) положить в каталог `takt_pt`. Сборка уже сделана с `base: '/takt_pt/'`, поэтому внутри `index.html` пути выглядят так: `src="/takt_pt/assets/index-*.js"`. Если увидишь `src="/assets/..."` — сборка устаревшая, останови выкладку и сообщи.

**Обязательно проверь SPA-fallback в nginx для `/takt_pt/`.** Это известный пробел: без него прямая ссылка или обновление страницы на `/takt_pt/incidents` вернёт 404. Нужен блок вида:

```nginx
location ^~ /takt_pt/ {
    root <корень сайта>;
    try_files $uri $uri/ /takt_pt/index.html;
}
```

Образец для подражания уже есть в репозитории — `nginx.takt-pt-arm.conf` в каталоге `takt_pt_arm`; в нём же заданы заголовки безопасности (CSP, X-Frame-Options, nosniff, Referrer-Policy, Permissions-Policy) и `Cache-Control: no-store`. Если для `/takt_pt/` таких заголовков нет — добавь по аналогии.

Любую правку конфига nginx делай так:

```bash
sudo cp /etc/nginx/<файл> /etc/nginx/<файл>.bak-$STAMP
# правка
sudo nginx -t && sudo systemctl reload nginx
```

Перезагружай nginx **только** после успешного `nginx -t`.

## Шаг 4. Проверка

Проверь снаружи (не только с localhost) и покажи результаты:

```bash
for u in https://ralta.ru/takt_pt_arm/ https://ralta.ru/takt_pt/ ; do
  curl -s -o /dev/null -w "$u -> %{http_code}\n" -L "$u"
done
```

Дополнительно:

1. `curl -s https://ralta.ru/takt_pt_arm/ | grep -o 'app.min.js?v=[0-9-]*'` → должно вернуть `v=20260803-03`.
2. `curl -s https://ralta.ru/takt_pt_arm/app.min.js | grep -c 'ГИПОТЕЗА\|hypothesis'` → больше нуля (признак, что залит новый код, а не старый из `.gz`).
3. `curl -s -o /dev/null -w '%{http_code}\n' https://ralta.ru/takt_pt/incidents` → **200**, а не 404 (проверка SPA-fallback).
4. `curl -s https://ralta.ru/takt_pt/ | grep -o 'src="[^"]*"'` → путь должен начинаться с `/takt_pt/assets/`.
5. API АРМ жив: `curl -s -o /dev/null -w '%{http_code}\n' https://ralta.ru/takt_pt_arm/health`.

В интерфейсе АРМ на экране расследования должны появиться новые блоки: «Принято от автоматики», «Гипотеза», «Уровни сущности», «Вердикт и выводы», вердикт в шапке и таймер разбора.

## Откат

Если что-то сломалось:

```bash
sudo rm -rf <корень>/takt_pt_arm && sudo mv <корень>/takt_pt_arm.pre-verdict-$STAMP <корень>/takt_pt_arm
sudo cp /etc/nginx/<файл>.bak-$STAMP /etc/nginx/<файл>
sudo nginx -t && sudo systemctl reload nginx
```

## Чего делать нельзя

- Не трогай другие сайты на этой ВМ: `torion.su`, `torion-shop` (включая `svoya-nota-app`), `zdorov-life`, каталоги `/opt/svoya-nota`, `/opt/torion`, их systemd-юниты и базы.
- Не удаляй существующие backup-каталоги `*.pre-*`.
- Не меняй бэкенд на порту 18092 и его конфигурацию — задача только про статику и nginx.
- Не правь файлы приложения напрямую на сервере: источник правды — репозиторий и каталоги на ПК.
- Не выполняй `systemctl restart nginx` (только `reload` после `nginx -t`).
