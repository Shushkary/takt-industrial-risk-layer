# Стенд «два источника» для проверки и отладки ТАКТ

Воспроизводимый стенд: два независимых фида событий (по умолчанию **EDR + OT**) сливаются
в хронологический поток, проходят полный конвейер ТАКТ (нормализация → обогащение →
инварианты → риск → кейс) и сверяются с размеченной истиной. На выходе — отчёт,
по которому видно не только «сколько собралось», но и **почему не собралось**.

## Зачем именно два источника

Один источник проверяет только детекцию инвариантов. Ценность ТАКТ — во втором эшелоне:
связать наблюдение из IT-домена (запуск процесса на АРМ) с наблюдением из OT-домена
(запись уставки в контур) в один кейс. Стенд из двух источников — минимальная конфигурация,
в которой эта связка вообще может быть проверена, и на которой сразу видны её ограничения.

## Быстрый старт (локально, без Docker)

```bash
python -m pip install -e ".[dev,metrics]"
python scripts/stand_dataset.py --pair edr,ot --incidents 6 --noise 300 --seed 7
python scripts/stand_run.py --reset
```

Результат: `data/stand/report/report.md` и `report.json`, БД стенда — `data/stand/takt.db`.
Каталог `data/` в `.gitignore`, стенд не засоряет репозиторий.

Живой API поверх наполненной БД (для АРМ, Swagger, ручной отладки):

```bash
TAKT_CONFIG=deploy/stand/risk_weights.stand.yaml TAKT_STORAGE=sqlite \
TAKT_SQLITE_PATH=data/stand/takt.db TAKT_PROFILE=dev TAKT_AUTH_REQUIRED=0 \
uvicorn takt.interface_adapters.api.main:app --host 127.0.0.1 --port 8090
```

## Быстрый старт (Docker)

```bash
docker compose -f deploy/stand/docker-compose.stand.yml --profile load run --rm stand-load
docker compose -f deploy/stand/docker-compose.stand.yml up -d api
curl -s localhost:8090/cases/stats
```

## Из чего состоит стенд

| Компонент | Файл | Роль |
|---|---|---|
| Генератор данных | `scripts/stand_dataset.py` | два CSV в формате `docs/pt_techlab/data_contract.md` + `ground_truth.json` |
| Прогон и отчёт | `scripts/stand_run.py` | слияние потоков, загрузка, метрики через HTTP, отчёт |
| Конфиг стенда | `deploy/stand/risk_weights.stand.yaml` | отличия от боевого конфига (см. ниже) |
| Живой контур | `deploy/stand/docker-compose.stand.yml` | API на данных стенда |
| Регрессия | `tests/test_stand_two_sources.py` | стенд не должен ломаться молча |

Пара источников меняется флагом: `--pair siem,ndr`, `--pair edr,siem`, `--pair ndr,ot` и т. д.
Поддержаны все четыре класса из ADR-001.

## Модель данных стенда

* **Фон** (`incident_id=BACKGROUND`) — независимые события: рабочие станции `ws-01…ws-12`,
  штатный опрос `plc-01…plc-03`, разрешённый DNS, успешные правила SIEM.
* **Инцидент** (`INC-001…`) — цепочка на **узле-пивоте** (`ews-01`, `ews-02`, `hmi-01`):
  запуск дроппера на АРМ → обращение к внешнему адресу → соединение в сторону PLC →
  `WRITE_SETPOINT` в контуре → `ADMIN_LOGIN` уже на самом PLC.

Пивот — инженерная станция или HMI, которую видят **оба** источника. Связок между IT и OT
две: общий `host_id` (правило `host_window`) и пара «оператор + адрес назначения»
(правило `user_destination`) — OT-строки несут колонку `operator_id` из контракта данных.

В `ground_truth.json` фон размечен как **отдельная группа на каждое событие**: связывание
двух не связанных событий одного узла — это false positive, и метрика обязана его считать.

## Отличия конфига стенда от боевого

| # | Отличие | Зачем |
|---|---|---|
| 1 | `correlation.mode: generalized` | в `config/risk_weights.yaml` стоит `legacy`, при котором `AssessRisk._correlation_candidates` возвращает пустой список и кросс-источниковая корреляция **полностью выключена** |
| 2 | Топология с пивотами `ews-01`, `hmi-01` | графовые инварианты должны видеть узлы стенда |
| 3 | Явный `ingest_trust.by_source` для `edr/siem/ndr/ot` | в боевом конфиге этих ключей нет, все четыре молча получают 1.0, и деградация DQ по источнику не проверяется |
| 4 | `storage.backend: sqlite`, `data/stand/takt.db` | отчёт и живой API читают одну БД |

`TAKT_CONFIG` обязан указывать внутрь корня репозитория — это проверяет
`ensure_explicit_takt_config_under_project`. Каталог инвариантов берётся из `config/invariants`,
потому что рядом со стендовым конфигом каталога `invariants/` нет.

## Что читать в отчёте

| Раздел | Что показывает | На что смотреть |
|---|---|---|
| Загрузка | принято/отказано, соб./с | отказы = расхождение CSV с контрактом данных |
| Состояние хранилища | события, кейсы, классы риска, DQ | «событий в поиске» ≠ «принято» → потеря в `recent_event_store` |
| Корреляция | pairwise precision/recall, кейсы с двумя источниками | recall падает — цепочки рвутся; precision падает — правила слишком широкие |
| Восстановление инцидентов | по каждой цепочке: сколько кейсов, **почему разъехалась** | готовый диагноз: разные `host_id` или пересечение границы окна |
| Покрытие правил | сколько событий каждого источника вообще дают отпечаток | «слепые источники» — правило для этого класса не работает никогда |
| Топ инвариантов | что сработало на корпусе | пусто → предикаты не видят полей после нормализации |

## Что стенд показал и что по этому сделано

Прогон `--pair edr,ot --incidents 6 --noise 300 --seed 7`.

**1. `correlation.mode: legacy` в боевом конфиге выключает обобщённый коррелятор целиком.**
На боевом конфиге стенд даёт 0 кейсов с двумя источниками — не потому что данные плохие.
Сам режим не меняли: это решение заказчика с последствиями для сертификации (ADR-001 в статусе
TBD). Но отключение перестало быть молчаливым — при `mode: legacy` с непустым списком правил
API пишет предупреждение на старте (`_warn_if_correlation_rules_are_inert`), а
`tests/test_stand_two_sources.py` фиксирует, что на боевом конфиге связок между источниками нет.

**2. Для класса `ot` были слепы два правила из трёх — исправлено наполовину.** `map_ot` терял
колонку `operator_id`, хотя контракт данных её предусматривает. Теперь она переносится в
`entities.user_id`, и OT участвует в правиле `user_destination` наравне с IT-источниками.
Артефакта `hash` у OT нет по природе данных — `file_hash` для него слеп by design.

| метрика | до правки | после |
|---|---:|---:|
| pairwise precision | 0.038 | 0.083 |
| pairwise recall | 0.333 | 0.667 |
| кейсов с двумя источниками | 3 | 6 |

**3. Цепочка рвётся на границе окна — дефект подтверждён, наивное лечение отвергнуто.**
`bucket_sec` режет по абсолютной сетке `timestamp // bucket_sec`, поэтому цепочка, начавшаяся
в `09:58`, попадает в два бакета. Очевидное решение — добавлять событию ещё и ключ предыдущего
окна — было реализовано и **измерено на стенде**: связывание становится транзитивным и склеивает
всю историю узла в один кейс.

| вариант | кейсов | precision | recall | кросс-источниковых |
|---|---:|---:|---:|---:|
| сетка окон (как сейчас) | 169 | 0.083 | 0.667 | 6 |
| перекрытие соседних окон | 64 | 0.005 | 0.500 | 5 |

Перекрытие хуже по всем осям, поэтому в код не пошло. Корректное решение — окно, привязанное
к временно́му интервалу кейса, а не к сетке; это отдельная задача проектирования, ограничение
записано в докстринге `correlation_fingerprints`.

**4. События OT, атрибутированные самому PLC, связываются с цепочкой только через оператора.**
`host_id` у них другой, адресных правил корреляции в конфиге нет. После правки 2 такие события
подхватываются правилом `user_destination`, если в выгрузке есть `operator_id`.

**5. Precision остаётся низкой (0.083) и это не артефакт разметки.** `host_window` с окном 600 с
на площадке из полутора десятков узлов склеивает фоновые события одного хоста. Числа выше — вход
в задачу сужения правил (например, требовать совпадения не только узла), а не повод править стенд.

## Ограничения

* Данные **синтетические**. Это не выгрузка заказчика и не доказательство качества детекции;
  для приёмки нужен обезличенный реальный срез (см. `docs/pt_techlab/data_contract.md`).
* Пропускная способность стенда (десятки–сотни соб./с) упирается в SQLite с фиксацией на
  событие и не является характеристикой продукта. Нагрузочные цифры — в
  `tests/test_risk_engine_100k_eps.py` и `tests/test_backtest_streaming_100k.py`.
* Стенд запускается с `TAKT_AUTH_REQUIRED=0`. Для КИИ-эксплуатации такой режим неприменим.
